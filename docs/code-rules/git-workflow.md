# 分支、提交与推送

这个仓库**从第一个 commit 起就是公开的**，所以这一篇的重点不是分支模型有多讲究，
而是：**推出去的东西撤不回来**。

---

## 分支

`main` 是唯一的长期分支，且**必须始终可运行**：clone 下来 `docker compose up` 能起、
CI 是绿的。README 上那三枚徽章是给第一次看到这个项目的人看的第一个信号，红着的
价值是负的。

- 小改动（文档、单文件修复）可以直接在 `main` 上提交
- **动结构、加功能、改依赖走 feature 分支 + PR**。commit 历史本身是作品的一部分，
  「这个人怎么推进一件事」比最终代码更能说明问题
- 分支名 `feat/<短名>`、`fix/<短名>`、`docs/<短名>`

---

## 提交信息

**中文，`范围: 做了什么`**，不用 `feat:` / `fix:` 这类英文前缀：

```
adpilot: D1-D2 骨架, FastAPI + 三库 + CI 全绿
README: 加 CI / Python / License 徽章
```

- 一句话说清**做了什么**，不是「改了哪些文件」——后者 `git show` 就能看到
- **动结构的改动，设计文档和代码进同一个 commit。** 分开提就会出现「文档说 A、
  代码是 B」的中间状态，而那个状态很可能永远留在历史里
- 别写「修复若干问题」这种什么也没说的标题

## 🔴 推送前的自检

每一次 `git push` 都是不可逆的公开动作。历史会留住你之后删掉的东西 —— 真要清干净
得重写每一个 commit hash，而 fork 和 clone 早就带走了。

**提交前扫一遍这四类：**

| 类别 | 具体 |
|---|---|
| 凭据 | `.env`、token、API key、数据库密码、私钥 |
| 客户身份 | 真实客户名、联系人、广告账户 ID、BM ID、结算价 |
| 真实数据 | 导出的报表、截图里的账户名和金额、seed 里的真实数字 |
| 内部信息 | 别的项目的名字、内部系统的地址、内部术语 |

`.gitignore` 挡住了第一类的常见形态，[命令守卫](../../.claude/bash_guard.py)会拦下
`git add .env` 和 `git add -f`。**但这两道都挡不住「把密钥粘进代码里」** —— 那只能
靠提交前自己看一眼 `git diff --staged`。

完整边界见[设计文档第八节](../design/2026-08-19-mvp-design.md)。

## 需要明确指令才能做的操作

以下都是对外或不可逆的，**必须等用户明确说了才执行**：

- `git push`（`.claude/settings.json` 里是 deny，会当场拦下）
- 任何形式的强制推送、`git rebase` 已推送的提交、`git reset --hard` 已推送的分支
- 打 tag、发 release
- 改仓库可见性、改 GitHub 上的任何设置

**用户说「提交」只意味着 commit 到当前分支，不等于 push。** 宁可多问一句。

---

## 不重写已推送的历史

`main` 上已经推出去的提交不 rebase、不 amend、不 force push。写错了就**再提一个
改回来的 commit**。

理由不是洁癖：这是公开仓库，别人可能已经 fork 或 clone；而且历史被重写之后，
「这个功能当时是怎么想的」那条线索就断了 —— 那条线索正是这个项目想展示的东西。
