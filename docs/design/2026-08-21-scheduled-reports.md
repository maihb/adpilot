# 定时日报设计

**范围**：D18，主设计文档第七节里**最后一条还打着 `[ ]` 的范围项**（Celery 异步
任务链，欠的就是「定时批量出日报」这一段）。

主文档是 [MVP 设计](2026-08-19-mvp-design.md)，日报本身的规则在
[LLM 日报与诊断](2026-08-21-llm-reports.md) 和 [reports.md](../business/reports.md)。
**这一篇不重复它们**，它回答的是：什么时候该出这一份、以及那个判断为什么不能看钟。

**与既有文档冲突的地方在文末列出，改动与代码进同一个 PR。**

## 一、原来那句话问错了问题

主设计文档 D14 那段注释是这么写的：

> 真正该异步的是**定时批量出日报**……它要先决定「几点算一天结束」，而那取决于
> 账户时区、每个账户还不一样。

**账户时区这件事其实早就解决了。** `ad_accounts.timezone` 建账户时必填，日报生成
也已经在用它（`services/report.py` 把它存进快照）。所以「这个账户的 08-20 什么时候
结束」是个已知量，一个查询就能算。

真正卡住的是**后面那一层**：日切了，不等于那天的数据在库里。

| | |
|---|---|
| MVP 不接 Ads API，数据靠人导 CSV | **日切了不等于数据到了** —— 运营可能第二天下午才导 |
| 就算接了 API，平台数据会回填 | 归因回传、无效流量剔除，同一天今天拉和三天后拉是两个数（[glossary](../business/glossary.md#数据会变回填与重述)） |
| 而日报是**快照** | 生成那一刻数字就固定了、此后不变。生成早了 = 把一个还会变的数固定成了发给客户的那份 |

所以该问的不是「几点算一天结束」，是「**这个账户那天的数据到齐了吗**」。

⚠️ 「到齐」永远判不准 —— 平台随时可能回填。这里要的不是「等到绝对准确」（那等不
来），而是**一个比钟表更好的信号**。而在这套系统里，那个信号是现成的：**归一化刚
往那一天写过东西**。

## 二、于是：两个触发口，一个判定

这个形状和告警巡检**一模一样**，而那不是巧合 —— 两者都是「反复跑也安全的对账」：

```
归一化跑完 ─┐
            ├─→ 同一个 due_reports() 判定 ─→ 对每个 due 的 (账户, 日期) 生成一份 draft
beat 每小时 ─┘
```

| 触发口 | 为什么要它 |
|---|---|
| **归一化完成后** | 数据刚进来，这是「到齐」最可靠的信号。没有它，一份下午导进来的 CSV 要等到下一个整点才出日报 |
| **beat 每小时一次** | 数据早就在库里、但那天当时还没结束（比如导的是当天的数据）。没有它，那天永远等不到下一次归一化，也就永远不会出日报 |

**每小时而不是每天一次**：账户时区各不相同，日切点散布在一天里的各个整点上。一天
扫一次的话，某些时区的账户要多等二十几个小时 —— 而日报的价值几乎全在及时性上。

🔴 **两个口调的是同一个函数，且它必须幂等。** `reports` 上有
`UniqueConstraint(account_id, stat_date)` 兜底，但判定阶段就该跳过已经有日报的那些
——靠捕异常去重会让日志里全是并发冲突，而真正的并发冲突就再也看不见了。

---

## 三、判定：三个条件，缺一不可

一个 `(账户, 日期)` **该出日报**，当且仅当：

| 条件 | 为什么 |
|---|---|
| 1. 那天在**账户时区**下已经结束，且已过 `report_delay_hours` | 见下一节 |
| 2. 那天**有 `daily_metrics` 数据** | 没数据的那天生成出来是一份空日报，而空日报比没有日报更糟 —— 它看起来像是「昨天什么都没花」 |
| 3. 那天**还没有任何日报**（含 draft） | 幂等。人可能正在改那份 draft，重新生成会把他改好的那版清掉（`generate` 的既有行为） |

外加两个账户级开关（下面第五节）：账户 `is_active`、且 `auto_report` 为真。

### 🔴 只看最近几天，不补历史

判定还要卡一条**窗口**：`stat_date` 不早于「今天往前数 `RECENT_DAYS`（3）天」。

不卡的话有个立刻会踩的坑：**运营补导一份跨 28 天的历史 CSV，归一化写了 28 天,
于是一口气生成 28 份日报 —— 以及 28 次 LLM 调用**。那是真金白银，而且没有人会看
三周前的日报。

3 天的理由：盖得住「周五的数据周一才导」这种常见的拖延，同时把「补历史」挡在外面。
⚠️ 待定参数，收口在 `services/report.py` 的 `RECENT_DAYS`。

---

## 四、`report_delay_hours`：它防的不是「等数据稳定」

日切之后等几小时才生成。**默认 2 小时**，per-account 可改。

先说清楚它**不是**什么：它不是「等到数据不再变」。平台数据在若干天内都还会变
（glossary 明写），等 7 天日报就没人看了。数字后来确实变了的处理方式是既有的那条
——**发新的一份并注明重述，不动老的那份**。

它防的是三件具体的事：

1. **日切瞬间的边界抖动。** 平台自己的日切也有延迟，`stat_date = 08-20` 的最后
   一批数据未必在 08-21 00:00:00 那一秒就位；
2. **夏令时切换日。** 那天在账户时区下不是 24 小时（`services/action.py` 的
   `window_bounds` 已经踩过这个），留一点余量比在边界上较真便宜；
3. **接了 Ads API 之后**「日切就拉」的冲动。到那天这个参数会变得比现在重要。

在 CSV 世界里它几乎不起作用 —— 因为条件 2（那天有数据）本身就是更强的门。这是
刻意的：**参数存在是为了那天接了 API 之后不用改结构**，不是为了现在调它。

⚠️ 待定参数。默认值收口在 `models/ad_account.py` 的列默认值。

## 五、账户上加两个字段

用户提的「账户基础信息配置」正是这一层。**但不是给客户填的** —— `/api/portal/*`
下一个写路由都没有，而那是 CLAUDE.md 硬规矩第 4 条：给客户端开写入口，漏一次作用域
就是 A 客户改了 B 客户的配置，**且不会有任何报错**。这两个字段在后台那条路径上，
由运营填。

| 字段 | 默认 | 为什么要它 |
|---|---|---|
| `auto_report` | `true` | 🔴 **它是省钱的闸门。** 并不是每个账户都要日报（内部测试账户、只看看板的客户），而没有这个开关，那些账户每天白烧一次 LLM 调用 |
| `report_delay_hours` | `2` | 见上一节 |

**为什么不用 `is_active` 兼这个职责**：停投的账户仍然要日报（复盘那几天怎么停的），
而不看日报的账户可能一直在投。两件事，两个开关。

## 六、🔴 绝不自动发布

生成出来的是 **`draft`**，到此为止。

发布的两条硬校验（人工修订过、操作记录非空）一条都不能松 —— 那是
[设计文档第五节](2026-08-19-mvp-design.md)那条边界的最后一道人工闸门：**模型可能在
散文里编一个百分比，没有机器拦得住，那道防线是人。**

所以这一段的价值要说准：它省掉的不是「审」，是「点生成然后等十几秒」。运营早上打开
后台，日报已经在那儿了，他只需要改人话、发布。

## 七、批量调 LLM 的三个护栏

定时批量生成 = 定时批量花钱，这一段比别处更要小心。

| 护栏 | 形态 |
|---|---|
| **一个账户失败不拖累其它** | 每个 `(账户, 日期)` 各自一个事务。一个账户的时区填错了，其余照常出 |
| **额度用光就停，不是继续试** | `QuotaExceededError` 当场中断整轮（不是跳过这一个继续），并把已生成的数报出来。继续试只会把剩下的调用全撞在同一堵墙上，然后日志里全是同一个错 |
| **LLM 挂了不阻塞日报** | 这是既有行为：没配 / 调不通时 `llm_narrative` 留空，日报照样生成（`_write_narrative` 直接 return）。运营自己写那段话，比没有日报强 |

⚠️ **这一轮不加「跳过已经失败过的」重试记账。** 日报是幂等的（那天没有就生成），
下一个整点自然会再试一次，不需要额外的状态。

## 八、不做什么

- ❌ **不自动发布**（第六节）。
- ❌ **不做「补生成历史」的入口。** 手动生成接口本来就能指定任意日期，定时这条只
  管最近几天。
- ❌ **不做每个账户各自的 cron 表达式。** 一小时一次的扫描 + 账户级的延迟参数已经
  覆盖了真实需求，而 per-account cron 要引入一个调度器，且「为什么这个账户没出日报」
  会变成一道需要读 crontab 的题。
- ❌ **不通知运营「今天有 N 份日报待审」。** 那是 [admin.md](../business/admin.md)
  里记着的「跨账户待办视图」，属于另一件事。
