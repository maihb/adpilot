# 登录验证码：连续失败两次后才出现

## 起因

部署到公网的那套实例原本挡着一层 nginx basic auth，现在要摘掉它（每次登录输两
道密码，而第一道并不比第二道强）。摘掉之后，**运营登录成为唯一的防线** ——
[auth.md](../business/auth.md) 的「已知残余」里那条「登录接口没有限流」从一个
可以接受的取舍变成了必须补的洞。

补法就是那条残余自己写的：Redis 计数器，加在 `api/auth.py` 的 `login`。差别只在
计数满了之后做什么 —— 这份文档回答的是这个。

## 不做什么，以及为什么

| 方案 | 为什么不做 |
|---|---|
| **锁定账号**（失败 N 次禁止登录 M 分钟） | 🔴 **这才是真正的拒绝服务。** 运营账号只有一个（`OPERATOR_USERNAME`，不建用户表），谁都能拿它去故意打错密码，把唯一能进后台的人锁在外面。验证码只增加攻击者的成本，不阻断合法用户 |
| **按 IP 限流** | 服务在 nginx + Cloudflare 后面，客户端 IP 只能从 `X-Forwarded-For` 读，而那个头可以伪造 —— 除非严格校验「上游确实是 CF 的 IP 段」并配 `real_ip_from`，那是部署形态的事，不该让应用层依赖一个它验证不了的前提 |
| **引 Pillow / captcha 库画图** | 为一个内部工具的验证码引一个几十兆的图像库不值。SVG 是纯字符串，浏览器原生渲染，零依赖 |
| **第三方验证码**（reCAPTCHA / hCaptcha） | 要把访问者的浏览器指纹送到第三方，而这个系统的主张是「数据不出自己的服务器」 |
| **一上来就要验证码** | 日常登录的是一两个人，每天几次。为了挡住不存在的攻击者，让他们每次都抄四个字符，是把成本加在唯一不该被打扰的人身上 |

**阈值定在 2 次**：一次是手滑，两次是没记住，三次开始像在试。

## 形状

```
前端打开登录框
      │
      ├─→ GET /api/auth/captcha?username=admin
      │     失败次数 < 2  →  {"required": false}                 不显示验证码框
      │     失败次数 ≥ 2  →  {"required": true, "captcha_id", "image"}  显示
      │
      └─→ POST /api/auth/login  {username, password, captcha_id?, captcha_answer?}
              │
              ├─ 1. 读失败计数
              ├─ 2. 需要验证码却没带 / 带错  →  401（**不做 argon2**）
              ├─ 3. 校验密码（argon2，到线程池）
              ├─ 4. 失败 → 计数 +1，401
              └─ 5. 成功 → 计数清零，签票
```

### 🔴 顺序就是安全性本身：验证码必须排在 argon2 之前

第 2 步放在第 3 步之前**不是为了省那几十毫秒**。argon2 慢是它的功能，而登录接口
免认证 —— 把验证码校验放在密码校验之后，攻击者照样能用一个空的 `captcha_answer`
驱动服务端做无限次 argon2，于是验证码没有降低爆破速率，只是让攻击者拿不到成功的
那次响应。**这与 `auth/token.py` 里「验签必须排在解析和过期判定之前」是同一类
要求：错了不会报错，只会悄悄失效。**

同理，**验证码用一次就删**（不管这次登录成不成功）。留着的话，一张过了的验证码
能被复用去驱动任意多次密码尝试，等于没有。

## 落位与分层

`auth/` 是纯计算层，**够不着 `db`**（[architecture.md](../code-rules/architecture.md)
的分层图），所以验证码这件事被拆成两半：

| 放哪 | 干什么 | 为什么在这一层 |
|---|---|---|
| `auth/captcha.py` | 出题、渲染 SVG、比对答案 | 全是纯函数：数据进、结论出，不碰任何 IO。于是它能用一张参数化表测完，不必起 Redis |
| `services/login_guard.py` | 失败计数、验证码答案的存取 | 状态在 Redis，而只有 `services` 及以上够得着 `db` |
| `api/auth.py` | 编排上面那五步 | 按 architecture.md 第 2 条，这一层只做「解析入参 → 调服务 → 翻状态码」 |

`api/deps.py` 补一个 `RedisDep` —— Redis 客户端此前只在 `resources.py` 里躺着，
没有任何路由用过它。

## 状态的形状

| 键 | 值 | TTL | 说明 |
|---|---|---|---|
| `login:fail:{username}` | 次数 | 15 分钟 | 每次失败重置 TTL：连续失败才累积，隔一阵再来是新的开始 |
| `login:captcha:{id}` | 答案（大写） | 5 分钟 | 用一次即删 |

**都不落 PostgreSQL。** 这是过程状态不是业务事实 —— Redis 整个丢了，最坏的后果
是所有人的失败计数清零，而那正是重启一次就该发生的事。

## 已知局限（写在这里是为了不假装它们不存在）

- **按用户名计数 ≈ 全局计数。** 只有一个运营账号，所以攻击者故意打错两次就能让
  真人也要抄验证码。这是**骚扰不是拒绝服务**，代价可接受；换成按 IP 才需要前面
  那个「验不了的前提」。
- **SVG 验证码挡不住 OCR。** 它挡的是「拿脚本无脑打一万次」，不是「有人专门写了
  个识别器来打这个后台」。真到了后者，该换的是部署形态（IP 白名单、CF Access、
  放进内网），不是把字符扭得更狠。
- **验证码不是限流。** 两者可以叠加，但这一版只做验证码 —— 阈值内的正常登录仍
  然一次 argon2，几十毫秒本身就是天然限速（`auth/password.py` 的模块 docstring）。
- **多实例下计数共享、验证码共享**，因为都在 Redis，这是选它而不是进程内存的
  唯一理由。
