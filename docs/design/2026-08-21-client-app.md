# 客户端（uni-app）设计

**范围**：D10–D11，给客户看的那个小程序 / H5。

前提已经在 [前端接入与认证方案](2026-08-21-client-auth.md) 里定完了 —— 认证怎么换、
作用域怎么锁、两个前端各自的位置。**这一篇不重复那些**，只回答「这个客户端本身
长什么样、为什么是这个样子」。接口清单和出参字段的真相源是
[`docs/business/portal.md`](../business/portal.md) 与 `schemas/portal.py`，
下文一概只指过去，不抄第二份。

**与主文档冲突的地方在文末「对既有文档的修改」里列出，改动与代码进同一个 PR。**

---

## 一、这一段和前九天有什么本质不同

前九天的每一条规矩最后都变成了机器判定：分层靠 `lint-imports`、作用域靠遍历
openapi.json 的门禁、签名比对靠扫源码的测试。**前端拿不到这套待遇**：

- **不做端到端测试**是已经定下的（[client-auth §8](2026-08-21-client-auth.md)），
  理由仍然成立 —— E2E 要起浏览器，在这个规模下维护成本高于收益；
- 它同时跑在**两个运行时**上（微信小程序的 JS 引擎、浏览器），行为不完全一致；
- 而它犯的错**是显示层的**：数字算对了、传对了，最后在屏幕上写错一个。后端没有
  任何办法发现这件事。

所以这一段的真实问题不是「写四个页面」，是：

> **在没有 E2E 的前提下，靠什么保证前端不把对的数据显示错。**

答案是三件，按可靠性排序：

1. **契约由生成的类型钉住**（§5）—— 后端改了出参形状，前端编译不过；
2. **口径跟着数据一起下发**（§4）—— 币种、时区、「这天没数据」都在出参里，前端
   不需要知道任何业务常识就能显示对；
3. **会算错的那几个数收进纯函数**（§9）—— 只有它们值得单测，页面不值得。

## 二、客户打开它，想知道什么

他是小商家。**他不看指标，他看结论。** 一次打开平均停留不到一分钟，回答三个问题：

| 他的问题 | 对应的东西 |
|---|---|
| 「昨天花了多少、效果怎么样」 | 一个账户的每日时间线 |
| 「余额还能撑几天」 | 可撑天数。**预充模式下归零就是停投**，这是全屏最该显眼的数字 |
| 「有没有什么事要我知道」 | 未解决的告警 |

四屏，不多不少：

> **D14 加了第五屏：日报。** 写这份设计时日报服务还不存在，所以当时的「四屏，
> 不多不少」是对的 —— 那一屏没有可显示的东西。日报的显示口径（对照期缺数据时
> 整段不做环比、不显示会跨天的操作时刻）记在
> [`docs/business/client-app.md`](../business/client-app.md)。

```
扫码页 ── 换到票 ──▶ 首页（账户列表 + 每个账户的可撑天数）
                        │
                        ├──▶ 账户详情（时间线）
                        ├──▶ 告警列表
                        └──▶ 关于（口径说明 + 退出）
```

**为什么首页是账户列表而不是一块大看板。** 客户手上的账户是个位数，但**币种和
时区可以各不相同**（示例数据里就有三种币种、三个时区）—— 把两个账户的花费加在
一起需要先决定汇率，而汇率是个全新的数据域，主文档里连它都还没有。首页做成
「一个账户一张卡」，是让「不能相加」这件事**在结构上说出来**，而不是靠一行小字
提醒。

**「关于」页不是凑数的。** 时区口径、归因差异、数据什么时候更新 —— 这三句话在
纸质日报里是固定附注，在客户端里必须有个地方放。没有它，客户拿平台后台的数字来
对，差一截就来问人，而那正是这套系统要省掉的沟通。

## 三、屏幕与数据来源

一屏一个接口，**没有任何页面需要两个接口拼**（首页除外，它按账户数并发取可撑天数）。

| 屏 | 用哪个 | 这屏为什么存在 |
|---|---|---|
| 扫码 / 输码 | `redeemInvite` | 唯一的入口。见 §7 |
| 首页 | `getPortalProfile` + `listPortalAccounts` + 每账户 `getPortalRunway` | 「我是谁 / 我有哪些号 / 哪个号快没钱了」 |
| 账户详情 | `listPortalMetrics` | 时间线。默认近 14 天 |
| 告警 | `listPortalAlerts` | 默认只给未解决的 |
| 关于 | 无 | 口径说明、退出登录 |

**首页的并发取数有个上限**：账户列表不分页、一次给完（后端页大小 100），而每个
账户要单独问一次可撑天数。个位数账户下这没问题，但**要在请求层限并发**（一次最多
5 个），否则小程序端的并发请求数上限（微信是 10）会把首页其余请求一起挤掉，症状是
「偶尔有个卡片空着」，且只在账户多的客户身上出现。

**默认 14 天不是随手定的**：`listPortalMetrics` 后端上限 92 天，但客户端首屏要快，
而 14 天正好覆盖「上周同一天」这个异动判定的基线周期（[alerts.md](../business/alerts.md)）
—— 客户看到告警说「比上周同日涨了 40%」时，那两天都在他眼前的这段线里。

## 四、🔴 四个「显示错了不会报错」的坑

这一节是整篇最要紧的部分。四件事共同的特点：**写错了页面照样渲染，数字照样有，
只是意思变了**，而没有任何测试或类型能拦下来。

### 1. 金额和比率全是字符串，`Number()` 是错的

后端的 `Decimal` 序列化出来**永远是 JSON 字符串**（`"123.4567"`），这是刻意的 ——
JS 的 `number` 是双精度浮点，而[「金额一律 Decimal」](../code-rules/conventions.md)
那条硬规矩在前端的延续就是「不要把它变回浮点」。

真正要命的是这一条：

```ts
Number(null) === 0   // ← 而 days_left: null 的意思是「无定义」
```

`days_left` 为 `null` 表示**近期没花钱，算不出可撑天数**。一个 `Number()` 就把
「不知道」变成了「还能撑 0 天」，于是每个暂停投放的账户都在客户屏幕上着火。
示例数据里的第四个账户专门演示这个边界。

**做法**：格式化函数只接受 `string | null`，`null` 一律走「—」分支，**不进算术**。
要比大小（比如给可撑天数上色）就比字符串转出来的数，但那个转换只出现在
`utils/decimal.ts` 一个文件里，页面里一次都不许出现 `Number(` 或 `parseFloat(`。
这条用 ESLint 的 `no-restricted-syntax` 钉住 —— 见 §9。

### 2. 没有数据的那天**不在数组里**

`listPortalMetrics` 不补零：「那天花了 0」和「那天没导入」是两件事
（[portal.md](../business/portal.md)）。前端只要按数组顺序连线，就等于宣称中间那
几天花了钱且是线性的。

**做法**：画之前先按日期展开成完整区间，缺的那天是 `null` 而不是 0，**线在那里
断开**。列表视图同理：缺的那天显示「未导入」，不显示 0。

### 3. 可撑天数是**三态**，不是一个数

| 出参 | 意思 | 显示 |
|---|---|---|
| `available` 为 `null` | 从没录过余额 | 「未录入」，灰色 |
| `days_left` 为 `null` 而 `available` 有值 | 有余额，近期没花钱 | 「暂无消耗」，灰色 |
| `days_left` 有值 | 真的能算 | 数字 + 按 `is_alerting` 上色 |

把前两种画成 0 天红色，是这个页面最容易犯也最伤客户信任的错。

还有一个次要的：`days_with_data` 明显小于回看窗口时，这个日均是拿不全的数据算的，
要显示一句「近 N 天里只有 M 天有数据」。不说的话，客户会拿一个被低估的日均去做
充值决定。

### 4. 币种和时区必须显示在数字旁边

`currency` 和 `timezone` 在出参里就是为了让前端把口径写出来
（`schemas/portal.py` 的注释原话）。**日期一律标成「账户时区下的自然日」**，
不做任何本地时区转换 —— 客户端把 `stat_date` 当成一个字符串标签，不要
`new Date()` 它，那一下会按客户手机的时区偏移一天。

## 五、契约：让生成的类型真的能用

[client-auth §6](2026-08-21-client-auth.md) 已经定了那道门禁的形状，并且把它挪到
「D10 第一件事」。真相源是 `Makefile` 的 `openapi` target 和 CI 的 frontend job。

### 导出 openapi.json 不要起服务

直觉做法是起后端、`curl /openapi.json`。别这么干：那要连数据库（lifespan 会开连接
池），而这道门禁的 job 不连任何外部服务；更别扭的是**生产环境那个路由是关掉的**
（`main.py` 里 `openapi_url=None`）。

正确做法是**离线调 `app.openapi()`** —— 它不走 HTTP、不触发 lifespan、不受
`openapi_url` 影响，因此也不需要任何依赖或凭据（`Settings` 在 dev 下允许空值，
凭据的非空校验只在 `prod` 生效）。收口在 `make openapi` 里。

### ~~`Decimal` 要收口成 `string`~~ —— 不用做，它本来就是对的

> **原稿在这里判断错了**（2026-08-21，D10 落地时验出来）。留着这段而不是删掉，
> 是因为**下一个人极可能重新犯一遍**：只要用 `Model.model_json_schema()` 去看，
> 看到的就是 `anyOf: [number, string]`。

原稿的说法是：Pydantic 给 `Decimal` 生成的 JSON Schema 是 `anyOf: [number, string]`，
于是生成出来的 TS 是 `number | string`，前端每个金额都要处理一个不可能出现的分支，
所以要加 `Money` / `Ratio` 别名把声明收成 `string`。

**实际验下来不需要，而且做了有害。** 关键在 Pydantic 的两个 schema 模式：

| 模式 | 谁在用 | `Decimal` 声明成 |
|---|---|---|
| validation | 请求体 | `number \| string`（**两种确实都收**，还带着 `minimum` 之类的约束） |
| serialization | 响应 | `string`（**下发的确实永远是字符串**） |

`model_json_schema()` 默认给的是 validation 那份，而 **FastAPI 对响应用的是
serialization 那份** —— 所以生成出来的 `spend: string`、`days_left: string | null`
从一开始就是对的、也是准确的。

加别名反而会把入参方向也压成 `string`，那既失真（后端真的两种都收），又会吃掉
`WithJsonSchema` 覆盖不了的 `Field(ge=0)` 约束 —— OpenAPI 上就看不到「余额不能
为负」了。

**§4.1 那个坑不受影响，反而更明确**：类型既然是 `string | null`，`Number()` 的
危险就是确定的，不是可能的。

## 六、token 在前端的生命周期

后端那半边已经通了（7 天票、滑动续期、首签起 90 天绝对上限）。前端要落三件事：

| 时机 | 做什么 |
|---|---|
| 换到票 | 存进 `uni.setStorageSync`，连同 `expires_at` 和 `client_name` |
| 每次冷启动 | 剩余有效期不足 **2 天**就静默续一次（`refreshClientToken`） |
| 收到 401 | **续一次**，成功就重放原请求；失败就清 token 回扫码页 |

🔴 **401 之后只准续一次。** 续期本身也可能 401（到了 90 天上限、或客户被停止合作），
那时如果还走「401 → 续期」的通路就是死循环，而在小程序里它表现为白屏转圈，不是
报错。请求层要有一个「本次启动已续过」的标志位。

**90 天上限那个终点要有话说。** 客户看到的必须是「登录已到期，请重新扫码」，不是
一个泛泛的网络错误 —— 那是这个方案里唯一的强制重新认证时刻，客户端不解释的话，
运营就要接一个「打不开了」的电话。

**退出登录只是删本地 token。** 自包含 token 撤销不了（[client-auth §4](2026-08-21-client-auth.md)），
所以「退出」在服务端没有任何对应动作。这句要写进「关于」页，别让人以为退出等于
把票作废了。

## 七、扫码这件事，两端不一样

这是 uni-app「一套代码两端跑」承诺里**唯一真正破掉的地方**，写清楚免得落地时才发现。

| | 微信小程序 | H5 |
|---|---|---|
| 摄像头扫码 | `uni.scanCode` 可用 | **没有**（浏览器没这个 API） |
| 进入方式 | 扫码，或手动输码 | **链接里带 `?code=`**，或手动输码 |

**二维码里放的是 H5 链接，不是小程序码。** 小程序码要通过平台接口生成，需要
AppID 和已发布的小程序 —— 而「不做微信授权登录」的理由（开源使用者大多没有企业
资质和备案）在这里一字不差地成立。运营侧生成的就是一个普通链接的二维码，微信里
扫出来在浏览器打开，能用；有小程序的使用者，客户可以在小程序里再扫一次同一个码。

**手动输码在两端都要有。** 它是所有扫码失败情形（截图转发、链接被聊天软件吃掉、
摄像头没权限）的唯一兜底，而它的实现成本是一个输入框。

⚠️ **邀请码进 URL 意味着它会进浏览器历史、也可能进转发记录。** 这是可接受的 ——
码本身有 30 天有效期、可作废、且换出去的票只能只读地看一个客户
（[client-auth §5](2026-08-21-client-auth.md)）。但前端要做一件事：**换到票之后
立刻把 URL 里的 `code` 参数抹掉**（`history.replaceState`），别让它留在地址栏被
截图。

## 八、代码怎么摆，选什么

目录位置 [client-auth §6](2026-08-21-client-auth.md) 已定（`client/`，与 `admin/`
平级，各自有 `src/api/generated/`）。这里只定内部结构和几个选型。

```
client/src/
  api/
    generated/     ← openapi-typescript 生成，不手写不手改
    request.ts     唯一的请求出口：挂 Authorization、限并发、401 续期
  stores/auth.ts   Pinia，只有这一个 store
  utils/
    decimal.ts     金额与比率的格式化。**页面里唯一允许碰字符串数字的地方**
    series.ts      时间线按日期展开、缺口留 null
  pages/           四个页面
```

| 决定 | 为什么 |
|---|---|
| **只有一个 Pinia store**（auth） | 数据是每日粒度的，缓存收益低而过期是 bug 源。页面各自请求，够快 |
| **UI 用 uni-ui** | 官方维护，两端行为一致。Vant / uView 的小程序适配各有各的坑，而这个客户端一共四屏，撑不起一个第三方组件库的调试成本 |
| **D10 不引图表库** | 小程序没有 DOM，ECharts 要走 canvas 适配层，两端渲染差异是纯粹的时间黑洞。先做「列表 + 每天一根 CSS 横条」，信息量足够回答 §2 那三个问题 |
| **图表放 D11，且是可砍的** | 真要引就用 uCharts（uni-app 生态原生走小程序 canvas）。⚠️ 引之前先读 §4.2：**折线上「断开」比列表里「未导入」更容易被画成 0** |
| **请求层单一出口** | 认证头、并发上限、401 续期只在一处。散在页面里的话，漏掉一个的症状是「某个页面偶尔要重新扫码」 |

## 九、CI：新增一个 frontend job

现有三个 job（quality / integration / docker）都不装 Node。新增第四个 `frontend`，它跑三件事：

| 步骤 | 拦的是什么 |
|---|---|
| 生成类型 → `git diff --exit-code` | **后端改了出参形状但没同步前端** |
| `vue-tsc --noEmit` | 前端用了不存在的字段（上一步生成的类型在这里生效） |
| `vitest run` | §4 里那三个纯函数算错了 |

**只测三样东西**，别扩：`utils/decimal.ts` 的 `null` 三态与字符串格式化、
`utils/series.ts` 的缺口展开、token 剩余有效期的判定。挑它们是因为它们满足同一个
条件 —— **错了不会报错，只会安静地显示成另一个意思**。页面渲染不测，那是 E2E 的
活，而 E2E 已经明确不做。

### 那条「禁止 `Number(`」的规则，写成 pytest 而不是 ESLint

原稿说加一条 `no-restricted-syntax`。落地时换成了扫源码的 pytest
（`tests/test_frontend_source.py`），两个理由：

- 规则本身只要**一条正则**，而为它引一整套 JS lint 工具链（eslint + vue 解析器
  + ts 解析器）要装的东西比被测的规则重得多；
- 放在 pytest 里它**跟着已有的五道门禁一起跑**，不必等 frontend job 装完 Node。

这和 `test_auth_token.py` 最后那条扫 `verify` 源码是同一个套路：**没有可观察行为
差异的事，只能盯代码形状**。同一个文件里顺带盯了另外两件：`uni.request` 只许出现
在唯一出口 `api/request.ts` 里，以及生成的类型确实进了 git（不进的话上面那道
`git diff --exit-code` 无从比起）。

⚠️ 这类门禁有个共同的失效模式：**路径写错就变成恒绿**。所以那个文件里第一条测试
先验「扫描目标真的在、且真的扫到了文件」。

**代价老实写下来**：CI 多一个装 Node 的 job，PR 反馈慢一点；`client/` 下会多出
`package-lock.json` 与一份生成的 `.ts`（后者进 git 是**故意的** —— 不进的话
`git diff --exit-code` 那道门禁就无从比起）。

## 十、演示路径：陌生人怎么在五分钟内看到它

README 承诺的是「陌生人 clone 能在五分钟内跑起来」，而客户端会给这句话添两个障碍：
微信开发者工具要装、小程序要 AppID。所以：

> **H5 是默认演示路径，小程序是可选项。**

```
docker compose up -d → migrate → seed（打印一个随机邀请码）
    → 起 client 的 H5 dev server → 粘贴那个码 → 看到看板
```

`make seed` 已经会打印一个可用的邀请码（它每次都不同，有测试盯着）。D10 要做的
是让 H5 能一条命令起来，并在 README 的快速开始里接上这一步。

**微信小程序端在 D10–D11 内要能真的跑一次**（验收标准就是「双端能跑」），但它的
运行步骤写进单独一节，不挡在主路径上 —— 一个陌生人评估这个项目时，不应该先被要求
去注册一个小程序账号。

## 十一、明确不做

[client-auth §8](2026-08-21-client-auth.md) 那六条继续有效（不做写操作、不做 App
打包、不做微信授权登录、不做 E2E…）。这一篇再加四条：

- ❌ **不做多账户合并视图**。要先决定换不换汇，而汇率是个全新数据域（同「库存断货」）
- ❌ **不做离线缓存 / 本地持久化数据**。除了 token，什么都不存。缓存过期在一个
  「每天更新一次」的场景里制造的困惑远多于它省下的那点等待
- ❌ **不做主题切换与多语言**。客户是中文小商家，`README.en.md` 是给读代码的人看的
- ❌ **不做站内消息或推送**。理由已在 [portal.md](../business/portal.md) 的「已知
  残余」里写明（模板消息要企业资质，短信要另一套服务），客户端只能被动打开看
