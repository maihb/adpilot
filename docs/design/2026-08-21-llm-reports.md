# LLM 日报与诊断设计

**范围**：D13–D14，主设计文档第五节那三件事里的前两件（日报撰写、异常诊断）。
知识库问答（RAG）不在这一段，理由见第九节。

主文档是 [MVP 设计](2026-08-19-mvp-design.md)，第五节已经把 AI 层的三条硬边界定
死了。**这一篇不重复那三条，它回答的是：怎么让它们从文档里的主张变成机器判定，
以及哪几条老实说变不了。**

**与既有文档冲突的地方在文末列出，改动与代码进同一个 PR。**

## 一、这一段的难点不在调模型

调一次 OpenAI 兼容的接口是这整段里最简单的部分。真正难的是两件事：

1. **让「LLM 只解释不决策」「LLM 不碰钱」变成机器保证**，而不是提示词里的一句
   话 —— 提示词是可以被绕过的，而且没有任何东西会因此报错；
2. **承认哪几条保证不了**，并且为它们留一道人工闸门。写下第 2 条比第 1 条更要紧：
   一个假装自己全自动的系统，会让人不再看它的输出。

顺带一提，日报里数字部分的**正确性从头到尾与 LLM 无关** —— 那些数字由
`daily_metrics` 算出来，和接口上查到的是同一份。LLM 只写那一行人话。

## 二、`llm/` 摆在哪，已经决定了一半

分层契约里 `llm` 的位置**早就画好了**（[architecture.md](../code-rules/architecture.md)
那张图里它和 `notifiers` 同层），只是目录还没建。那个位置很低：

```
services                  ← 业务逻辑
schemas                   ← 对外形状
models                    ← 表结构
providers | db | notifiers | llm     ← 🔴 llm 在这里
auth | rules
```

**只允许自下而上依赖**，于是 `llm/` 够不着 `models`、`schemas`、`services`、`db`。
具体后果：

| 想在 `llm/` 里写的 | 结果 |
|---|---|
| `select(...)` 查一下这个账户的历史 | 契约当场拦下（够不着 `db` / `models`） |
| 把生成的日报存进库 | 同上 —— **它根本写不了库** |
| 调 `services.balance.record(...)` 去改点什么 | 同上 |
| import `schemas.portal.PortalMetricDay` 当输入类型 | 同上 |

**这就是「LLM 不做决策」的机器形态。** 它比提示词硬得多：LLM 层连业务对象都摸不
到，唯一能做的事是「一段结构化输入进去、一段结构化输出出来」。要改任何东西，只能
由 `services/` 拿着那个输出去做，而那一步是确定性代码，人能 review。

⚠️ **建 `src/adpilot/llm/` 目录的那一刻，`lint-imports` 会红。** 契约开着
`exhaustive`，新顶层模块必须先在 `pyproject.toml` 的 layers 表里占位 —— 那是刻意
的（配置里那段注释点名说了 `rules` 和 `llm`）。**先改契约，再建目录。**

### 于是 `llm/` 要有自己的一套契约类型

它 import 不到 `schemas/`，所以输入输出的 Pydantic 模型得自己定义（`llm/contracts.py`）。
这看起来像重复，其实是好事：**LLM 层的契约和对外 API 的契约本来就该分开演进**。
`services/` 负责把业务数据翻译成 LLM 的输入形状 —— 那一层翻译是显式的、可读的，
而不是「把 ORM 对象直接扔给模型」。

## 三、🔴 数字不由 LLM 产生

日报由两部分组成，**它们的来源必须分开**：

| 部分 | 谁产生 | 例子 |
|---|---|---|
| 数字 | 代码，从 `daily_metrics` 算 | 花费、CPA、环比、可撑天数 |
| 人话 | LLM | 「成本上升是周末 CPM 普涨，未做调整，观察到周一」 |

**做法是让 LLM 的输出 schema 里只有文字字段。** 它填不进数字字段 —— 那些字段在
它的契约里根本不存在。于是「LLM 把 CPA 编成了另一个值」在结构上不可能发生。

### 但它写的散文里仍然可能编数字 —— 这条保证不了

`summary: str` 里写「成本上升了 40%」，而实际是 24% —— **没有任何机器判定能可靠
地拦住它**。可以想到的办法都不好：正则抽数字再比对，会被「四成」「近一半」绕过去；
让模型只输出模板槽位，那就等于放弃了「那一行人话」本身的价值。

所以这里不假装能防住，而是**为它留一道人工闸门**：

> **日报必须经人工修订才能发布。** 这不是流程洁癖，它是数字正确性的最后一道防线。

主文档第十节第 4 条已经定了「发布日报前校验操作记录非空」，这里再加一条同源的：
**未经人工确认的日报不能进入客户可见的那条路径**。两条都写成 `services/` 里的
硬校验，不是 UI 上的提示。

## 四、日报的生命周期

```
draft ──LLM 写完──▶ pending_review ──人工修订──▶ published ──▶ 客户可见
  ▲                                                    │
  └──────── LLM 失败时也会到这里（人话字段为空）────────┘
```

四个约束，每个都有理由：

| 约束 | 为什么 |
|---|---|
| **两版都存**（LLM 原文 + 人工修订后） | 主文档第六节已定。要能回答「这句话是模型写的还是人改的」——那是评估这套系统值不值得信的唯一依据 |
| **只有 `published` 的日报走 `/api/portal/*`** | 客户不该看到草稿。这条是**作用域之外的第二把锁**，写在 `services/` 的查询条件里 |
| **发布即快照固定** | 见下 |
| **LLM 失败不阻塞** | 数字部分是确定性的，不该被模型的可用性绑架。人话字段留空并标注「未生成」，人可以自己写 |

### 「发布即快照固定」是什么意思

那天的指标**后来可能变**：平台回填、重新导入一份更全的报表、归一化重跑。而日报
已经发给客户了。

**已发布的日报不跟着变。** 它存的是发布那一刻的数字快照，不是一个每次查询都重算
的视图。理由：客户手里那份 PDF / 截图 / 聊天记录不会自己更新，而一个「同一天的
日报今天看和昨天看数字不一样」的系统，会让人怀疑全部数字。

数字后来修正了怎么办 —— 在新一期日报里说明，那正是「本期做了什么」该写的内容。

## 五、成本、提示词版本、失败降级

### `llm_calls` 记什么，为什么

主文档第六节列了这张表。它至少要能回答三个问题：

| 问题 | 需要记 |
|---|---|
| 这个月花了多少 | prompt / completion token 数、预估成本、模型名 |
| **三个月后那份日报是什么口径生成的** | **提示词版本号** |
| 那次为什么失败 | 结果状态、重试次数、错误类型（**不记响应正文** —— 那里面可能有客户数据） |

**提示词版本号是这里最容易被漏掉、也最难补的一个字段。** 提示词改一次，日报的
口径就变了一次，而没有版本号的话，三个月后没有任何办法把「这份日报」和「当时那
版提示词」对上。这和主文档第二节第 5 条（平台字段会漂移，上个月的口径三个月后要
查得到）是同一个理由。

约定：提示词是**代码里的常量**，带一个显式的版本号；改内容必须改版本号。有一条
测试盯着「版本号变了没有」——它不判内容好坏，只判「改了却没升版本」。

### 成本上限

每次调用记成本，并给一个**每日调用次数上限**（可配，默认宽松）。超了拒绝执行，
而不是继续花钱。

这不是省钱，是防失控：一个写错的循环可以在夜里把额度跑光，而它花的是使用者自己
的钱 —— 自托管意味着没有人替他兜底。

> **「记一条告警」这半句落地时改掉了**（2026-08-21，D13）。`alerts` 的每一行都挂
> 在一个广告账户上（`account_id` 非空，去重键也带着它），而「实例的额度用光了」是
> 系统级的事 —— 塞进去要么造一条挂在随机账户上的假告警，要么把那张表改成「有时挂
> 账户、有时不挂」，两条都比它想解决的问题更糟。实际形态：调用方拿到 **429**，
> 日志里有 `llm_daily_quota_exceeded`。真要让它显眼起来，那是「系统级通知」这件
> 独立的事，不该借告警表的壳。

## 六、适配器：MVP 只做 OpenAI 兼容（对主文档的收缩）

主文档第十节第 2 条写着「Claude / Gemini 各写一个原生适配器放在 `providers/` 下
作为示例，同时也是『适配器注册表』这个设计的活证明」。

**这一段只做 OpenAI 兼容那一个**，加一个测试用的假实现。三个理由：

1. **Claude 和 Gemini 都提供 OpenAI 兼容端点。** 换供应商改三个环境变量就行，
   原生适配器带来的增量是「用上它们特有的功能」（prompt caching、thinking 之类），
   而写日报用不到那些；
2. 「注册表设计能用」这个证明**已经由 `providers/` 给出了** —— 那里真有多个实现
   （文件导入已落地，平台 API 的接口已预留）。为同一个设计再写两个用不上的实现，
   是为了证明而写代码；
3. 两天里塞三个适配器，只会让每个都写得潦草。

`LLMProvider` 的接口照样留好，这是**接口预留而不是省略**——和不接 Ads API 那个
决定同源。

## 七、异常诊断：按需，不自动

告警产生时**不自动**调 LLM 诊断。运营在后台点一下才诊断。

理由是告警的构成：大部分告警一眼就知道原因（余额低了 → 充钱；花费涨了 → 昨天调过
预算）。给每条都自动花一次钱，钱花在了不需要解释的那些上面，而**诊断的价值恰恰在
难解释的少数**。

诊断的输出同样受第三节那条约束：它给的是「大概率是素材疲劳，频次已到 3.2，建议换
素材而不是降价」这类**解释和方向**，schema 里没有任何「把预算改成 X」的字段 ——
主文档第五节第 1 条那条硬边界的机器形态。

## 八、测什么，不测什么

| 测 | 怎么测 |
|---|---|
| schema 校验失败会重试、重试仍失败会抛 | 假 provider 按次序返回坏输出、好输出 |
| **token 用量和成本被记下来了** | 断言 `llm_calls` 里有行、字段非空 |
| LLM 失败时日报**照样生成**（人话字段为空） | 假 provider 直接抛 |
| 未经人工修订的日报**发不出去** | 直接调 `services`，断言抛领域异常 |
| 已发布的日报**不随指标变化** | 发布 → 改 `daily_metrics` → 再查，数字不变 |
| 提示词改了但版本号没改 | 扫源码（同 `test_auth_token.py` 那条的套路） |

**不测**：那一行人话写得好不好。它没有确定的正确答案，而为它写断言只会得到一个
「模型换一次就红一次」的测试。CI 里**一次真实的模型调用都不发** —— 那会让构建
依赖外部服务和一把 API key。

## 九、明确不做

- ❌ **不做 RAG 知识库问答**。主文档第五节列了它，但它要一个全新的数据域（语料
  导入、切分、向量库）——那是独立的一段，不该塞进这两天。接口不预留，等真要做时
  它的形状会和现在想的不一样
- ❌ **不做自动执行任何建议**（主文档第五节第 1 条，永久有效）
- ❌ **不做周报 / 月报**。日报的口径先跑通，周期汇总有它自己的坑（`reach` 跨天
  不可加，见 [glossary](../business/glossary.md)）
- ❌ **不做多模型对比 / 投票**。一个自托管的小系统，把同一份输入发给三个模型再
  投票，成本翻三倍换来的确定性提升不明显
- ❌ **不做流式输出**。日报是异步生成的，没有人盯着屏幕等它一个字一个字出来
- ❌ **不在 CI 里发真实模型调用**（见上节）

## 十、里程碑拆分

| 天 | 产出 | 验收标准 |
|---|---|---|
| **D13** | `llm/` 层 + 成本记录 + 操作记录 | ① 契约先占位再建目录，`make imports` 绿；② 假 provider 下走通「结构化输入 → schema 校验 → 落 `llm_calls`」；③ 操作记录能建能查（日报的前置依赖） |
| **D14** | 日报生成 / 修订 / 发布 + 诊断 | ① 一份日报从 draft 到 published 走完，客户端能看到已发布的那份；② 未经修订的发不出去、操作记录为空的发不出去，两条都有测试；③ LLM 挂掉时日报照样生成，人话字段标注「未生成」 |

**如果两天不够，先砍异常诊断**（第七节那件），保日报那条链。理由：日报是每天都要
交付的东西，诊断是锦上添花；而且诊断的输入依赖告警，告警本身已经能用了。

⚠️ **操作记录（`actions`）排在 D13 而不是 D14**：它是日报「本期做了什么」那段的
唯一数据来源，而主文档第十节第 4 条要求发布前校验它非空。先有它，日报那条链才完整。
