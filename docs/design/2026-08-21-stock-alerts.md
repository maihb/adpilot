# 库存断货预警设计

**范围**：D16，主设计文档第二节第 3 个真实问题、第七节范围里**最后一个没打勾的
功能项**。

主文档是 [MVP 设计](2026-08-19-mvp-design.md)，公式在
[glossary](../business/glossary.md#库存可撑天数) 里早就定了：

```
stock_days_left = stock_qty / avg_daily_sales
```

**这一篇不重复那个公式，它回答的是**：那个分母从哪来（我们手上没有订单数据）、
商品挂在谁身上、以及为此动 `alerts` 表要付什么代价。

**与既有文档冲突的地方在文末列出，改动与代码进同一个 PR。**

---

## 一、难点不在公式，在「数据不在同一个后台」

余额那条规则的两个数都在手边：余额是人录的，日均消耗从 `daily_metrics` 算。
库存这条一个都不在 ——

| 要的数 | 在哪 | 我们有没有 |
|---|---|---|
| 当前库存 | 店铺后台（Shopify / TikTok 小店 / 独立站） | ❌ 得导进来 |
| 日均销量 | 同上，订单模块 | ❌ **而且导出未必有这一列** |

设计文档第二节把这件事说得很直白：「库存数据在店铺后台、投放数据在广告后台，
**两边没人对**」。所以这一段真正要解决的不是除法，是**把另一个系统里的数搬过来
并且承认它是稀疏的、不连续的、有时缺列的**。

下面三节分别是这三件事的落点。

---

## 二、库存快照不走 Mongo，直接落 PG

已有的导入链是「文件 → Mongo `raw_reports` → 归一化 → PG」。库存**刻意不复用它**。

理由是双库那条边界本身（`db/mongo.py` 的模块 docstring 是真相源）：Mongo 那一层
存在的理由是**平台字段会漂移，而原始事实要能回溯审计、能重跑归一化**。库存这边
两个前提都不成立 ——

- 表的形状**由我们自己定**（一份导入模板：SKU、名称、库存、日均销量）。没有哪个
  平台在改它，也就没有「三个月后要查当时是什么口径」这个问题；
- 快照本身**已经是归一化后的形态**。SKU 是 SKU、件数是件数，中间没有一次需要留
  痕的解释。

为一份自定义模板再走一遍「原始快照 → 归一化」，是把机制当仪式：多两个失败点、多
一次异步等待，换来的审计价值是零。

> ⚠️ **接了店铺 API 之后这条要重看。** 那时进来的是平台的原始 JSON，字段会漂移、
> 会有归因口径 —— 那份响应该进 Mongo，和广告报表一样。这条决定的适用范围是
> 「人按模板整理好的文件」，不是「库存数据」这个类别。

## 三、🔴 商品挂在**客户**上，于是 `alerts` 表要改

### 为什么不挂账户

一个客户可以同时投 Meta 和 TikTok 两个广告账户，推的是**同一批货**。挂在账户上，
同一个 SKU 就有两份库存记录，然后：

- 两份会打架（哪份是真的？），
- 补货的时候要记得改两处，漏一处就是一条假告警，
- 而告警长得跟真的一模一样。

库存是**店铺的属性，不是投放账户的属性**。唯一键因此是 `(client_id, sku)`。

### 代价：`alerts.account_id` 一直是必填的

告警表现在长这样：`account_id` NOT NULL，去重靠部分唯一索引
`(account_id, kind, subject) WHERE status = 'open'`。库存告警**不属于任何一个
账户**，塞不进去。

三个选项，选第三个：

| 选项 | 为什么不 |
|---|---|
| 库存告警挂到「该客户的每个在投账户」 | 一次断货变成 N 条一模一样的告警，而 N 是账户数 |
| 库存不进 `alerts`，只做一个现算清单接口 | 那就没有状态机 —— 每小时巡检一次的东西，没有「只说一遍」就是每天七十多条 |
| **`alerts` 加 `client_id`，`account_id` 改可空** | ✅ 见下 |

改动本身很小：

- `client_id` NOT NULL —— **每条告警都属于某个客户**，账户级的从账户推导得出；
- `account_id` 可空 —— `NULL` 的意思是「这条告警是客户级的，不指向任何账户」。

顺带的好处：`services/alert.py` 的 `list_for_client` 不用再 JOIN 回 `ad_accounts`
了，作用域过滤变成一个等值条件。作用域那条硬规矩（CLAUDE.md 第 4 条）说的是
「漏一次不会有任何报错」，而少一次 JOIN 就是少一个漏的地方。

### 🔴 那个不写就每小时多一条告警的坑

**PostgreSQL 的唯一索引里 `NULL` 不等于 `NULL`。**

于是现有那个部分索引 `(account_id, kind, subject) WHERE status='open'` 对
`account_id IS NULL` 的行**形同虚设** —— 两条一模一样的客户级库存告警不会冲突，
巡检每小时新开一条，一天二十四条，而每一条看起来都对。

所以要**再加一个部分索引**，专管客户级那一半：

```
(client_id, kind, subject) WHERE status = 'open' AND account_id IS NULL
```

两个索引各管一半，互不重叠。⚠️ 部分索引是 autogenerate 的盲区
（[Schema 方案第四节](2026-08-19-schema-migration.md)），这一份迁移**必须手写**
并且手工核对 —— 现有那个 `uq_alerts_open_subject` 当初就是这么进来的。

> 用 `COALESCE(account_id, 0)` 把两个索引并成一个也行，代价是索引表达式更难读、
> 且 `0` 这个魔法值会在未来某次 review 里被人问「哪个账户是 0 号」。两个部分索引
> 各自说清自己管什么，更便宜。

## 四、分母：日均销量从哪来

公式的分子（当前库存）就在快照里。分母是这一段真正的设计。

### 两个来源，优先级写死

| 来源 | 什么时候用 | 怎么来 |
|---|---|---|
| **导入文件里的一列** | 有这一列就用它 | 店铺后台大多导得出「近 30 天日均销量」之类 |
| **从快照序列自己推** | 没有那一列时 | 相邻两次快照之间库存掉了多少，就是这段时间卖了多少 |
| 都没有 | 兜底 | `null` —— **无定义，不告警** |

第二条是这一段唯一有点意思的地方，也是唯一有坑的地方。

### 推算：只认下降段，但「没动」要算进分母

```
avg_daily_sales = Σ(相邻两点的库存降幅) / Σ(那些段覆盖的天数)
```

两条边界，方向刚好相反，都得写清楚：

| 相邻两点 | 算不算 | 为什么 |
|---|---|---|
| 库存**下降** | ✅ 降幅计入销量，跨度计入天数 | 正常消耗 |
| 库存**没动** | ✅ 销量记 0，**跨度照样计入天数** | 「三天没卖出去」是**可信的信息**，不是缺数据。丢掉它会让日均被系统性高估 |
| 库存**上升** | ❌ 整段跳过 | 补货了。「补了 100 卖了 20」和「补了 80 卖了 0」在两个端点上看**完全一样**，硬拆只能靠猜 |

中间那条是从余额那条规则原样搬过来的：那边「暂停投放的日子有指标行、`spend`
是 0，本来就该拉低日均」，这边「没卖出去的日子库存没动，本来就该拉低日均」——
**区分「没数据」和「没发生」，是这两条规则共用的那个分母的全部意义。**

### 🔴 两个防止算出胡话的上限

- **跨度超过 `MAX_SPAN_DAYS`（30）的相邻两点，整段不算。** 三个月前传过一次、
  今天又传一次，中间发生过什么（补了几轮、断了几次）完全不知道，拿两个端点相减
  除以 90 天算出来的「日均」是个精确的胡话。
- **取最近 `LOOKBACK_POINTS`（8）条快照，不按天窗口截。** 这条和余额那边刻意不
  一样：库存快照的时间密度由**人的导入节奏**决定，不由日历决定。硬按 7 天窗口
  切，「一周传一次」的客户永远只剩一个点、永远算不出日均 —— 而导得少的客户恰恰
  是盯得少的那批，最需要这条规则。

⚠️ 三个参数（`LOOKBACK_POINTS`、`MAX_SPAN_DAYS`、下一节的阈值）全部收口在
`rules/stock.py`，并在 glossary 里记成「待定」。

## 五、阈值是 7 天，不是余额那个 3 天

同一个语义（「留给人反应的时间」），两条规则落成两个数，因为反应链路不是一回事：

| | 余额 | 库存 |
|---|---|---|
| 发现之后要做什么 | 通知客户 → 客户充值 | 通知客户 → 客户下单 → 生产/发货 → 入仓 |
| 那件事有多快 | **分钟级**（网银点一下） | **周级** |
| 阈值 | 3 天 | **7 天** |

把库存也设成 3 天，等于在货已经来不及补的时候才开始提醒 —— 告警照样准，但没用。

⚠️ 待定参数，收口在 `rules/stock.py` 的 `ALERT_THRESHOLD_DAYS`。

## 六、录入：只有批量导入，且重传是幂等的

**和余额刚好相反，两条都是。**

| | 余额 | 库存 | 为什么不同 |
|---|---|---|---|
| 入口 | 单条录入接口 | **只有 CSV 批量** | 余额一个账户一个数，手工录合理；库存一个客户几十上百个 SKU，手工录不现实 |
| 重复提交 | **409** | **覆盖** | 余额是人手敲的，两次提交是误操作；库存是文件上传，**重传同一份是常态**（网络断了、发现少了一列重来） |

其余三条与余额一致，理由也一致：

- **`captured_at` 是「这份库存属于哪一刻」**，不是上传时间。人可能今天补传昨天
  导的表。
- **快照只增不改**（同一时刻的同一个 SKU 除外，见上）。「上周五这个款还剩多少」
  是会被回头追问的问题。
- **商品本身是 upsert**（名字会改），**快照是 append**。

还有一条是库存独有的：

🔴 **文件里没出现的 SKU 一律不动，不视为库存归零。** 部分导出是常态（只导主推款、
只导某个分类），把「这次没导」读成「卖光了」，会让每一次部分导入都炸出一屏假告警。

## 七、不做什么

- ❌ **不做「哪个广告在推这个 SKU」的映射。** 那要一张人手工维护的对照表，而它会
  立刻腐化（换素材、改系列名、一个系列推多个款）。告警说清「哪个客户的哪个 SKU
  快断了」，剩下的判断交给人 —— 这与设计文档第五节「LLM 只建议不执行」是同一种
  克制：**系统只负责把两个后台的数摆到一起，不替人做那个关联。**
- ❌ **日报里不加库存段。** 日报的数字口径已经固定住了（快照结构、两版人话、
  LLM 输出契约），为库存加一段要同时动这四处，而库存告警已经能在告警清单和客户端
  看到。范围外。
- ❌ **不接店铺 API。** 与不接 Ads API 同一个理由（设计文档第四节），且更甚 ——
  店铺侧的形态比广告平台更碎（自建站、SaaS、ERP 各一套）。
- ❌ **不做库存趋势图。** 快照都在，画图是前端的事，等有人真的要看再说。

## 八、客户没有在投账户时，不巡检它的库存

这条容易被写反，所以单列一节。

断货告警的全部意义是「**广告还在跑，货没了**」。客户所有账户都停投时，库存不足只
是一条店铺经营信息，不是投放告警 —— 报出来只会稀释清单，而清单的价值和它的长度成
反比（这句话在 [alerts.md](../business/alerts.md) 里已经为「只看两个指标」写过
一次）。

所以巡检的入口是：**先取有在投账户的客户，再看它们的商品。** 商品自己也有
`is_active` —— 下架的款不看，同 `ad_accounts.is_active`。

与告警状态机既有的那条一致：**已经开着的库存告警不会因为账户停投而自动
resolve**，那需要一次确认问题不在了，不是靠「看不见了」。
