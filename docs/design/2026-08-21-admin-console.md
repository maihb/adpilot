# 内部后台（Vue 3）设计

**范围**：D12，运营自己用的那个操作台。

认证与作用域的前提已经在
[前端接入与认证方案](2026-08-21-client-auth.md) 里定完了，客户端那一半的经验在
[客户端设计](2026-08-21-client-app.md)。**这一篇只回答后台自己的问题**：它长什么样、
它和客户端有什么根本不同、以及那些「点下去就收不回来」的操作该怎么摆。

接口清单的真相源是 openapi.json 与 [`docs/business/`](../business/) 各篇，下文一概
只指过去。**与既有文档冲突的地方在文末列出，改动与代码进同一个 PR。**

---

## 一、和客户端的三个根本不同

|  | 客户端（D10–D11） | 内部后台（D12） |
|---|---|---|
| 能看什么 | 一个客户，只读 | **所有**客户，可写 |
| token | 7 天，滑动续期到 90 天 | **8 小时，不滑动** |
| 在哪用 | 公网，手机 | 运营自己的电脑 |
| 最大的风险 | 把对的数据**显示错** | 把错的操作**执行对** |

最后一行是这一篇的主线。客户端那四条口径规则防的是「显示成另一个意思」，而后台
里同一类失误的后果不同 —— **它会改掉数据、切断某个客户的访问、或者往库里灌一份
串了账户的报表**，而这些都没有撤销键。

所以后台的设计重心不在信息密度（虽然 Element Plus 那栏写着「密度优先」），在
**让不可逆的操作难做、让可逆的操作好做**。

---

## 二、为什么不和客户端共用代码

两个前端都要：一个请求出口、一份生成的类型、一套 token 存取。看起来该抽一层。
**不抽**，三个理由：

1. **运行时不同。** 客户端跑在 uni-app 上，请求走 `uni.request`；后台是普通
   浏览器应用，走 `fetch`。抽出来的「共同层」会立刻长出两个分支。
2. **契约本来就要独立**（[client-auth §2](2026-08-21-client-auth.md)）。客户端只
   依赖 `/api/portal/*`，后台依赖其余八组 —— 后台重构不该波及已经发到客户手机上
   的小程序。
3. **真正相同的逻辑只有几十行**（存 token、判过期、拼 query）。为它引一个 monorepo
   工具链（workspace、共享包、构建顺序）的成本，比重写那几十行高一个量级。

**唯一要复用的是那道类型生成门禁**：同一份 `openapi.json` 生成两份 `.ts`，
`make openapi` 一次生成两边，CI 里一起 `git diff --exit-code`。复用的是**机制**，
不是代码。

## 三、屏幕，按运营真实的一天排

| 屏 | 运营什么时候用它 | 主要接口 |
|---|---|---|
| 登录 | 每天早上一次（token 8 小时） | `login` |
| **导入** | **每天，最高频** | `importReportFile` → `getTaskStatus` |
| **告警** | **每天，第二高频** | `listAlerts` · `sweepAlerts` |
| 客户列表 / 新建 | 新客户上手时 | `listClients` · `createClient` |
| 客户详情 | 发邀请码、停用客户 | `listAdAccounts` · `listInvites` · `createInvite` · `revokeInvite` |
| 账户详情 | 核对数字、录余额 | `listDailyMetrics` · `recordBalance` · `normalizeAccount` |

**导入排在最前**，因为它是这个系统要替掉的那件手工活本身（设计文档第二节第 1 条）。
一个每天要用的页面藏在两层菜单后面，运营就会退回去用 Excel。

**没有仪表盘首页。** 登录后直接进导入页。做一个「今日概览」很好看，但它回答的问题
（哪个账户花超了）告警页已经在回答，而且回答得更准 —— 两个地方说同一件事，早晚
会有一天说得不一样。

## 四、🔴 写操作：按「能不能收回来」分三类

滥用二次确认等于没有确认 —— 每个操作都弹一次窗，人就会条件反射地点「确定」。
所以按后果分级，**只有第三类拦**：

| 类别 | 例子 | UI 怎么做 |
|---|---|---|
| 可逆 | 建客户、建账户、改名字、录余额 | 直接做，出错了再改回来 |
| 难逆 | 导入一份报表 | 直接做，但**导完必须显示导进去了什么**（见第五节）—— `raw_reports` 是 append-only，导错了删不掉，只能靠归一化重跑盖过去 |
| **不可逆 / 立刻影响外部人** | **停用客户**、**作废邀请码** | 二次确认，且确认文案里写出后果 |

**停用客户是全系统唯一一个「点下去立刻影响外部人」的操作**：`require_client_scope`
每次请求都查一遍 `is_active`，所以那个客户手上还没过期的票**当场失效**
（[client-auth §3](2026-08-21-client-auth.md)）。确认框里必须说这句话，不能只写
「确定停用吗」。

### 邀请码明文只出现一次

`InviteCreatedResponse` 是明文码**唯一**出现的地方，列表接口只有状态（库里存的是
哈希，还原不回来）。这对 UI 是硬约束，不是提示语的问题：

- 生成之后**不能是一个转瞬即逝的 toast**。要留在页面上，带一个复制按钮，直到
  运营主动关掉；
- 关掉之前要说清楚「关掉就再也看不到了，需要的话现在就发出去」；
- 列表里那些历史邀请码**不显示码**，只显示状态（发于何时、用过几次、什么时候过期）
  —— 这一点要在 UI 上说明白，否则运营会以为是页面坏了。

## 五、导入在 UI 上是**两段**，不是一件事

后端这条链刻意做成一半同步一半异步（主设计文档第七节那段说明）：

```
上传 → 解析（同步，在请求里）→ 落 Mongo 快照 → 排一个归一化任务（异步）
                ↑                                      ↑
        失败当场说，因为人还盯着屏幕          task_id，去 /api/tasks/{id} 看
```

**这两段在界面上必须分得开。** 只显示一个「导入成功」的话，运营会以为数字已经能查
了，而实际上归一化可能还在队列里、也可能失败了。

三个具体要求：

1. **解析失败要显示细节。** 后端在认不出日期列时会把表头列出来 —— 那正是运营要拿
   去改导出设置的信息，吞掉它等于让人去猜。
2. **`task_id` 可能是 `null`。** 队列连不上时快照照样落好，只是没人接着跑。这时
   界面要说「已存下，但归一化没排上队」，并给一个手动触发的入口（`normalizeAccount`）
   —— 而不是显示一个永远转圈的进度条。
3. **轮询要有终点。** 拿 `getTaskStatus` 轮询，但设一个上限（比如 30 次），到了就
   停下来告诉人「还没跑完，去任务里看」。无限轮询的页面在标签页留一夜之后，会把
   日志刷满。

⚠️ 上传上限 **10 MiB**，超了后端回 413。前端要在**选文件时就拦**并说明白 —— 传完
几十兆再告诉人不行，那几十兆是白传的。

## 六、8 小时的票，以及「填到一半过期」

后台 token 8 小时、**不做滑动续期到某个上限**（客户端那套是为「常看的人不用重扫」，
而这里权限大得多）。有 `refreshToken` 可以主动换新，但过期了就只能重登。

真正的坑不在过期本身，在**过期时人正填着东西**：

- 建客户填了一半、导入选好了文件 —— 一个粗暴的「跳回登录页」会把这些全丢掉；
- 而运营那时的反应是「这破系统」，然后重新填一遍。

**做法**：401 之后不跳转，就地弹一个登录框；登录成功后**重放刚才那个请求**，页面
状态一动不动。这比客户端那套复杂，值得 —— 客户端上丢掉的只是一次只读请求。

⚠️ **重放只对幂等的请求安全。** 导入不是幂等的（`raw_reports` append-only，重放
会多一份快照）。所以：**只重放 GET，写操作让人重新点一次**。那一次重点是自愿的，
而一次悄悄的重复导入没人会发现。

## 七、Element Plus 按需引入

全量引入 Element Plus 是 2 MB 量级的 JS + CSS。后台是内网工具，慢一点不致命，但
「陌生人 clone 下来跑一遍」是这个项目的主目标，而一个首屏几秒的演示会直接影响
判断。

用 `unplugin-vue-components` + `unplugin-auto-import` 按需引入。代价是多两个构建期
插件，收益是产物只带用到的那十来个组件。

**不引 UI 之外的任何框架**：没有状态管理库（后台的状态就是「当前 token」和「当前
页的数据」，`ref` 足够）、没有请求库（`fetch` 够用）、没有图表库（同客户端，理由
见 [client-app §8](2026-08-21-client-app.md)）。

## 八、类型生成：一份 openapi，两份 `.ts`

`make openapi` 现在只生成客户端那份，要扩成两份。两边**不共用生成物**：
客户端只需要 `/api/portal/*` 那几个 schema，后台需要其余全部 —— 但
`openapi-typescript` 不做按路径裁剪，所以两份内容其实高度重合。

**接受这个重复**，因为替代方案（手写一个裁剪步骤）是在生成链里塞一个只有我们自己
懂的环节，而它一旦出错，症状是「类型对不上但说不清为什么」。

CI 的 `frontend` job 相应扩成：生成两份 → `git diff --exit-code` 一次盖住两边 →
两边各跑 `type-check`。

## 九、暴露面：它和客户端不该是同一个入口

客户端要暴露在公网（客户在手机上看），后台不该。但 MVP **不做**网络层隔离
（nginx 规则、IP 白名单、VPN）——那是部署形态的事，而这个项目连部署脚本都还没有。

**MVP 的立场写清楚**：后台的唯一防线是运营的账号密码 + 8 小时 token，
`OPERATOR_PASSWORD_HASH` 用 argon2 存哈希。这够不够取决于部署的人把它放在哪，
而那句话要写进 README 的部署一节，不能默认没人会把它直接挂公网。

## 十、明确不做

- ❌ **不做用户管理**（[client-auth §8](2026-08-21-client-auth.md) 已定，运营账号
  从环境变量来）
- ❌ **不做仪表盘首页**（见第三节）
- ❌ **不做日报编辑与发布** —— 日报服务本身要等 D13–D14。主文档第七节那条把它算在
  D12 里，**这一篇把它挪走**，理由见文末
- ❌ **不做删除**。客户、账户、指标都没有删除接口，后台也不提供 —— 停用（`is_active`）
  能解决所有真实需求，而删除会让历史数据变成孤儿
- ❌ **不做批量操作**。批量导入、批量发码这类功能，在「几个客户」的规模下省不下
  多少时间，却把每个操作的后果放大了 N 倍
- ❌ **不做前端的端到端测试**（同客户端）。那三个「算错了不会报错」的纯函数照样
  单测，页面渲染不测

## 十一、里程碑

| 天 | 产出 | 验收标准 |
|---|---|---|
| **D12** | 内部后台可用 | ① 登录 → 导入一份 CSV → 看到解析结果与归一化任务状态；② 建一个客户 → 给它发一个邀请码 → 那个码能在客户端换到票；③ 停用那个客户 → 客户端**当场**看不到数据；④ `frontend` job 覆盖两个前端且在 CI 里绿 |

第 ③ 条是这一天真正的验收：它同时验证了后台的写操作、客户端的作用域、以及
`require_client_scope` 每次请求查 `is_active` 那个刻意的额外查询 —— **三样东西在
一条链上，任何一处坏了它都不成立**。
