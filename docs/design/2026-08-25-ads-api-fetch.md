# 自动拉取平台数据（TikTok 先行）

> 状态：设计。里程碑 D19。
> 前置：[MVP 设计文档 §4「数据接入：MVP 不接 Ads API」](2026-08-19-mvp-design.md)
> 里那句「凭据到位当天可插上」，现在到了兑现它的时候。

## 一、要解决什么

MVP 的数据入口只有一个：有人从平台后台导出 CSV，再上传进来。它替掉了「手工把
数字抄进表格」，但没替掉「每天有人记得去导一次」——而**忘了导的那天，系统显示的
不是「没数据」，是一片正常的空白**。

自动拉取要解决的就是这一件事：让「昨天花了多少」不依赖任何人的记性。

**顺带解决的第二件事**：余额目前是[手工录入](../business/balances.md)的。而余额
归零在预充模式下等于广告**停投**（不是降速），停一次赔掉 3–5 天学习期。一条最痛
的规则，依据却是「有没有人记得去录一条」——这个组合本身就是设计缺陷。TikTok 的
`/advertiser/info/` 直接给 `balance`，跟日指标同一次拉取周期，几乎不加成本。

## 二、为什么是 TikTok，不是两个平台一起

**不是技术选择，是审批周期决定的。**

| | 拿到凭据要多久 | 门槛 |
|---|---|---|
| Meta | 分钟级 | BM 里建 System User 就有，token 不过期，访问自有账户不需要 App Review |
| TikTok | 数个工作日到数周 | Business Center onboarding → sandbox → app review → 业务验证 → 数据合规审计 |

而真实在跑量的客户账户在 TikTok。Meta 那条路更好走，但**走通了也没有数据可拉**
——这正是 MVP 当初决定不接 API 的同一个理由，只是这次反过来用。

所以：**这一版只落 TikTok 一个 provider**，但协议、凭据存储、排期、失败可见性
全部按「会有第二个平台」来设计。Meta 适配器是后面加一个文件的事，上游不改。

## 三、🔴 最重要的一条：拉不到数必须比拉错数更显眼

手工导入有个隐含的好处：**导的人知道自己导了没有。** 自动化把这个「知道」拿走了，
于是失败的默认呈现方式变成了——

> 昨天花费 $0，曝光 0，点击 0。

**这不是异常状态，这是「昨天没投放」的正常长相。** 看板上它和真实的停投一模一样，
日报会照常生成，余额告警会因为「没有新消耗」而安静下来。整套系统会非常自信地
给出一个基于空气的结论。

这条推出三个硬性要求，它们比拉取本身更重要：

1. **每次拉取的结局都要落在库里**（成功/失败、什么时候、错在哪），不是只写日志。
   日志没人看，而这件事必须能被查询和告警。
2. **失败要开告警**，走既有的[告警状态机](../business/alerts.md)（同一个故障不
   重复打扰，恢复了自动关闭）。
3. **「该有数据却没有」本身是一种失败**。拉取 HTTP 200 但返回零行，与拉取报错
   在后果上是同一件事——账户在投放、平台却说没有数据，这时候要**保留昨天的判断
   不动**，而不是写一行 0 进去。

⚠️ 第 3 条有个例外必须写清楚：**账户真的停投时，零行就是正确答案**。区分办法不是
猜，是看 `ad_accounts.is_active` 和（第七节的）投放状态——两者都说在投却拿回零行，
才是故障。这也是这一版要拉「账户/系列状态」的真正理由，它不只是个展示字段。

## 四、协议：加 `fetch`，不动 `parse`

`providers/base.py` 的 docstring 早就把做法定死了：**统一产物，不统一入口**。这一版
照做，并把当初没写的两件事补上。

### 4.1 为什么是两个 Protocol 而不是一个

```
ReportProvider.parse(content) -> ParseResult      # 推送型：CSV，同步，CPU 密集
FetchProvider.fetch(...)      -> ParseResult      # 拉取型：API，异步，IO 密集
```

同步/异步这条线跨不过去：`parse` 必须留在 `asyncio.to_thread` 里（几千行 CSV 在
事件循环里解析会卡住**整个进程**的所有请求），而 `fetch` 是纯网络等待，丢进线程池
只是白占一个线程。硬凑成一个方法的下场是所有调用点都要先判断「这个 provider 是
哪种」——那正是 Protocol 想消掉的东西。

**共用的是 `ParseResult`/`RawRows`**，于是落快照、归一化、重跑、审计全是同一套代码。

### 4.2 provider 不认识 `MetricLevel`

`providers/` 在分层契约里与 `db` 同层，**不 import 任何 adpilot 内部模块**——这是
`base.py` 开宗明义的第一句，不能为了省事破掉。

所以 `fetch` 收的层级是 `str`（`"campaign"` / `"ad"`），由 `services/` 传
`level.value` 进来，provider 自己把它翻译成平台方言（TikTok 的
`data_level=AUCTION_CAMPAIGN`、维度 `campaign_id` + `stat_time_day`）。翻译表长在
各 provider 内部，因为它就是平台特有的知识。

### 4.3 🔴 `ParseError` 不够用了：两种失败要走不同的结局

CSV 世界里失败只有一种：文件不对。API 世界里有两种，而**把它们混在一起会让系统
在最坏的情况下最安静**：

| 失败 | 例子 | 正确结局 |
|---|---|---|
| **瞬时** | 限流、502、连接超时 | 退避重试，多半自己会好 |
| **确定性** | token 过期/被撤销、advertiser_id 不对、权限不足 | **立即停止重试，开告警** |

重试一个已经过期的 token，五次退避之后任务安静地失败，而 result backend 里的记录
一天后就过期了。第二天没人发现，第三天日报里的「花费 0」看起来还是很正常。

所以新增 `FetchError(message, *, retryable: bool)`，由 provider 按平台错误码判定
——**判定表是平台知识，属于 provider，不属于 services**。`tasks/` 那一层照既有分工
处理：不可重试的转成 `Reject(requeue=False)` 进死信队列，同时开告警。

## 五、凭据：加密落库，不进 env

### 5.1 为什么不是 env

`.env` 装得下 LLM key 和数据库密码，装不下这个：

* OAuth token 是**运行时产物**——人在后台点「授权」，平台回调过来才有。部署时不
  存在这个值，没法写进 env。
* token 会**变**（撤销后重新授权、换客户、多个 BC）。改 env 要重启进程。
* 一把 token 对应一批 advertiser_id，多客户多账户之后 env 里会长出
  `TIKTOK_TOKEN_1/2/3` 这种东西，而它们和 `ad_accounts` 的对应关系无处安放。

### 5.2 落库就必须加密，理由不是「加密比较好」

数据库 dump 会被拷来拷去（备份、迁移、本地复现问题）。**一份明文 token 的 dump
等于把广告账户的读取权限装进了一个会被邮件传来传去的文件**。

做法：新表 `platform_credentials`，token 用 `CREDENTIALS_SECRET`（env，必填，
**无默认值**——CLAUDE.md 硬规矩 2）派生的密钥加密后存。

🔴 **`CREDENTIALS_SECRET` 丢了 = 所有 token 全部解不开，只能重新走一遍授权。**
它和 `AUTH_SECRET` 不同：后者丢了只是所有人重新登录一次。这条要写进部署文档和
凭据存档，不能只活在代码注释里。

⚠️ 加密**不防**「有人能读数据库 + 能读 env」，那时两样都在他手上。它防的是这两者
分头泄露——而分头泄露恰恰是最常见的形态（dump 传出去了、env 没有；日志里带出了
env、数据库没有）。

### 5.3 凭据挂在授权上，不挂在账户上

TikTok 一次授权返回的是一**批** `advertiser_ids`。所以：

```
platform_credentials  (一次授权 = 一行)
        ▲
        │ credential_id (可空)
   ad_accounts
```

`ad_accounts.credential_id` **可空**是刻意的：CSV 导入的账户永远不会有凭据，而
「没接 API」不是一种残缺状态，是这个系统一直支持的正常形态。**这也是自动拉取的
开关**——不挂凭据就不会被排期扫到，不需要再加一个 `auto_fetch` 布尔。

### 5.4 OAuth 回调这个接口是个洞，必须堵

`GET /api/oauth/tiktok/callback` 是平台带着 `auth_code` 重定向过来的**浏览器
跳转**，带不了 `Authorization` 头 → 它只能进
[`test_auth_guard.py`](../../tests/test_auth_guard.py) 那份显式豁免清单。

豁免 = 公网上任何人都能打这个地址。防护是 OAuth 的 `state` 参数：发起授权时用
`AUTH_SECRET` 签一个短期 token 塞进 `state`，回调时验签 + 验过期，对不上直接拒。
**签发和验证复用 `auth/token.py` 那一套**（那里的 `compare_digest` 和「验签排在
解析之前」有测试盯着，另起一套等于把那些保证扔掉重来）。

## 六、拉多少天：滚动窗口，不是「拉昨天」

**每次拉最近 N 天（默认 3），不是只拉昨天。**

平台数据在若干天内还会变（归因回传、无效流量剔除、汇率重算，见
[glossary](../business/glossary.md)「回填与重述」）。只拉昨天，那些后来的修正
就永远进不来了。

**这一条几乎不花额外成本，因为架构早就为它准备好了**：快照 append-only（多拉一天
就是多一条快照，不覆盖任何东西），归一化按 `(账户, 层级, 对象, 日期)` upsert
（同一天拉三次也不会变成三倍花费）。滚动窗口在这套结构上是免费的——**这正是当初
养第二个数据库换来的东西**。

窗口长度做成账户级配置还是全局常量？**全局常量**。理由是它现在没有分账户调整的
理由，而一个「每个账户都能填但所有人都填一样」的字段，只会在将来某天被填错一个。

## 七、拉三样东西，落三个地方

| 拉什么 | TikTok 接口 | 落到 |
|---|---|---|
| 日指标 | `/report/integrated/get/` | Mongo 快照 → 归一化 → `daily_metrics`（既有链路，一行不改） |
| 余额 | `/advertiser/info/` | `balances`（既有表，`note` 写明「自动拉取」） |
| 投放状态 | `/campaign/get/` `/adgroup/get/` | **新表** `platform_objects`（当前态，upsert） |

### 7.1 状态为什么要单独一张表

`daily_metrics` 是**日切事实**（那天花了多少，永不改变）。投放状态是**当前态**
（现在是开着还是关着），两者混在一起会立刻出问题：昨天的行要不要跟着今天的状态
变化更新？答案无论是什么都是错的。

`platform_objects` 存最新态，唯一键 `(account_id, level, object_id)`，每次拉取
upsert。它同时喂三件事：

1. 第三节那条「在投却零花费 = 故障」的判据；
2. 「预算花超了自动停」这类平台侧的静默停投——`secondary_status` 里写着，而日
   指标里只表现为「今天没花钱」；
3. 日报里那句「哪些系列在跑」，现在只能靠人记。

⚠️ 状态快照**也进 Mongo**，和日指标同样 append-only。理由：「那天它到底是不是
开着的」是个会被回头追问的问题（尤其在客户说「我明明让你停了」的时候），而 PG
里只有最新态。

### 7.2 余额那条为什么不建新表

`balances` 已经是「时点量 + 只增不改」的形状，自动拉取塞进去正好。唯一要注意的是
`captured_at` 取**平台返回的时刻**而不是拉取时刻——同一天充值前后是两个数，这张表
的全部价值就在于分得清哪一刻。

## 八、排期：第 40 分，且这个数字不是随手挑的

beat 现在有两个任务：整点巡检告警、第 20 分定时日报（[两者错开是刻意的](2026-08-21-scheduled-reports.md)，
有测试盯着不许撞）。拉取放**第 40 分**。

顺序上它是这样接起来的：

```
:40 拉取 ──20分钟窗口──▶ :00 巡检（用刚拉到的数判告警）──20分钟──▶ :20 日报（引用刚开的告警）
```

**20 分钟是留给拉取跑完的余量**：多账户 × 多层级 × 退避重试，比两条 SQL 慢得多。
放在 :50 会更「新鲜」，但拉取一慢就会和巡检抢在同一时刻，而那时谁先跑完取决于
worker 取消息的顺序——正是既有那条排期规则要避免的情形。

于是 `db/broker.py` 里变成三个常量互不相等，[`tests/test_tasks.py`](../../tests/test_tasks.py)
那条断言要从「两个不等」扩成「三个两两不等」。

**触发条件仍然是「数据到齐了吗」而不是「几点了」**，沿用定时日报那一版的判据形状：
账户时区下日切 + `report_delay_hours` 到了才拉那一天。密集排期靠判定便宜——绝大多数
轮次扫出来是空的。

## 九、手动触发这条路必须留着

`POST /api/ad-accounts/{id}/fetch`（可带日期区间）。三个场景要它：

* 授权刚配好，想立刻验证通不通，而不是等到下一个整点；
* 平台回填了很久以前的数据，要重拉一段历史；
* 排期那次失败了，修好之后补一次。

它和排期共用同一个服务函数——**排期任务只是「按条件挑出账户，然后调它」**。两条
路径各写一份实现的话，将来必然有一条先腐化，而腐化的那条通常是没人天天看的那条。

## 十、明确不做（防止范围蔓延）

* ❌ **Redis 令牌桶限流。** `config.py` 里那句注释是给将来留的。这一版账户数是
  个位数，串行 + 指数退避够用；上令牌桶要先有「被限流了」的实测，而现在连一次
  真实调用都还没发生过。
* ❌ **自动创建/修改广告。** 申请 scope 时就只勾读权限——让「代客户改预算」在
  **凭据层面**做不到，这比任何提示词边界都硬（MVP 设计文档第五节第 1 条）。
* ❌ **Meta 适配器。** 见第二节。协议留好，凭据到位当天加一个文件。
* ❌ **拉素材/评论/受众。** 与日报和告警无关。
* ❌ **实时拉取。** 广告数据的最小有意义粒度是天，分钟级刷新只是把限流额度烧掉。

## 十一、分两步落地

第一步跑通了才有第二步，因为第二步的价值完全依赖第一步的链路是真的通的：

| 步 | 内容 | 验收 |
|---|---|---|
| **一** | `FetchProvider` 协议 + TikTok provider（日指标 + 余额）+ 凭据表与加密 + OAuth 授权链路 + 手动触发接口 + 拉取结局落库与告警 | 沙盒账户点一次「立即拉取」，`daily_metrics` 出行、`balances` 出一条；把 token 改错，能看到一条 `fetch_failed` 告警而不是一片安静 |
| **二** | 投放状态（`platform_objects`）+ beat 排期 + 「在投却零花费」判据 + 后台页面 | 一整夜无人值守，早上日报里的数字来自 API 而不是谁的手工导入 |

## 十二、已知残余

* **沙盒和生产的差异没法预先验证。** base_url 做成可配，但沙盒返回的字段是否与
  生产完全一致，只有审核通过之后才知道。字段映射一旦要改，改的是
  `services/field_maps.py` 一个文件——这是当初把映射收口在那里的回报。
* **token 刷新没做。** TikTok 的 access_token 长期有效，没有刷新流程；表上留了
  `expires_at`（可空）是为了 Meta——那边的短期 token 有 60 天大限。真接 Meta 时
  才写刷新逻辑，现在写等于写一段永远不执行的代码。
* **一次拉取里部分账户失败怎么办**：各账户各记各的结局，不互相中断。**但整轮不
  中断这件事和日报那条「撞额度就整轮中断」是相反的取舍**——理由是拉取不花钱，
  而一个账户的 token 失效不该让其他账户也停更。
* **历史回补要人手动发起。** 接上 API 之前的日子只能靠 CSV 导入或手动触发拉一段
  区间，没有「自动把过去 90 天补齐」的按钮。真要补的时候手动触发接口够用了。
