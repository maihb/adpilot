# 前端接入与认证方案

**范围**：给客户看的 uni-app 客户端、给运营用的 Vue 3 内部后台，以及**这两件事
共同的前提** —— 认证与授权作用域。

主设计文档是 [`2026-08-19-mvp-design.md`](2026-08-19-mvp-design.md)，这一篇只展开
它第七节列的两个前端和第十节第 3 条定下的登录方向。**与主文档冲突的地方在文末
「对主文档的修改」里列出，改动与代码进同一个 PR。**

---

## 一、为什么这一段不只是「写个前端」

**现在这套接口是裸的。** 8 组接口（`clients` / `metrics` / `balances` / `alerts` /
`imports` / `tasks`…）没有任何认证 —— 任何能连到 8000 端口的人都可以建客户、导数据、
翻出全部客户的花费。D1–D8 这样是合理的：那八天里唯一的调用方是 Swagger 和
`curl`，加认证只会拖慢每一次手工验证。

但客户端一上来，这件事就不能再拖：

- 客户端是**给外部客户用的**，它必然要暴露在公网上；
- README 承诺「陌生人 clone 能在五分钟内跑起来」，而陌生人很可能直接部署到一台
  有公网 IP 的机器上。此时「只保护客户端那套接口」等于把写接口留在门外。

所以这一段的真实内容是三件事，前端只是最后一件：

1. **认证层**（谁在调）
2. **授权作用域**（这个人能看到哪些数据）
3. 两个前端

## 二、两类使用者，两套接口

| | 运营（内部后台） | 客户（uni-app） |
|---|---|---|
| 是谁 | 部署这套系统的人，可能只有一两个 | 被服务的小商家 |
| 能做什么 | 建客户、导数据、编辑发布日报、看**所有**客户 | 只读，且**只看自己** |
| 从哪来 | 内网或运营自己的电脑 | 公网，微信小程序 / H5 |
| 认证方式 | 账号密码 → 短期 token | 扫码 → 短期 token |

**接口分成两组，不共用 handler：**

```
/api/...          内部接口（现有全部 8 组，加上认证）
/api/portal/...   客户端接口（只读，作用域锁死在一个客户上）
```

> **落地时从 `/api/client/` 改成了 `/api/portal/`**（2026-08-21，D9）。两个理由：
> `api/client.py` 已经是客户管理的路由文件，同名目录建不出来；更要紧的是
> `/api/clients`（运营管客户）和 `/api/client/...`（客户看自己）**只差一个 `s`，
> 而两者的授权模型正好相反** —— review 一段路径字符串时，那个差别小到不足以让人
> 停下来。`portal` 让模块名、tag 和路径三者一致，作用域门禁也按这个前缀扫。

不做成「同一套接口 + 在 handler 里判断身份」，三个理由：

1. **`api/` 不写业务判断**是已有的硬规矩（[architecture.md](../code-rules/architecture.md)
   第 2 条）。身份分支写进每个 handler，正是那条规矩要挡的东西。
2. **出参形状本来就不同。** 客户不该看到内部备注（`Client.note`）、结算相关字段、
   别的客户存在过的痕迹。同一个 response model 服务两类人，早晚会漏字段 —— 而漏
   的方向是往外漏。
3. **契约独立。** 客户端只依赖 `/api/client/*`，内部接口重构不会波及已经发到客户
   手机上的小程序 —— 小程序发版要审核，改不动。

代价是有一部分查询逻辑会在两边各调一次 `services/`。这是**刻意的重复**：重复的是
调用，不是逻辑，`services/` 仍然是唯一实现。

## 三、授权作用域：这不是多租户

主设计文档写着「**不做多租户 SaaS 化**（单实例单使用者，多客户是业务概念不是租户
隔离）」，而客户端登录后显然只能看自己的数据 —— 这两句不矛盾，但**必须说清楚差别，
否则下一个人会照着「多租户」的思路去加 `tenant_id`**：

- **多租户**说的是「多个**使用者**（多家代运营公司）共用一个实例，彼此的数据在存储
  层就要隔离」。这个不做，`clients` 表里也永远不该出现 `tenant_id`。
- **授权作用域**说的是「同一个使用者的数据里，这个访问者能看到哪一部分」。这个必须
  做，它是**读取路径上的过滤**，不是存储层的隔离。

实现上的落点：客户端 token 里带着 `client_id`，`/api/client/*` 的每一个查询都必须
按它过滤。

### 🔴 作用域不能靠自觉

「每个 handler 记得加一句 `where client_id == ...`」是行不通的 —— 漏一次的后果是
把 A 客户的花费给 B 客户看见，而这种漏**不会有任何报错**，测试也测不出来（除非
专门为它写用例）。

所以要有机器保证，分两层：

1. **`/api/client/*` 下的每个路由都必须声明 `ClientScopeDep`**，由它从 token 解出
   `client_id`。有一条测试遍历 OpenAPI 里 `/client/` 开头的全部路由，检查这个依赖
   在不在 —— 加了新路由却忘了它，CI 红。这和 `test_business_docs.py` 拿 tag 当锚点
   是同一个套路：**挑一个「忘了就注册不出来」的东西去验**。
2. **客户端用的 service 函数，`client_id` 是必填关键字参数**，不给默认值。想查
   「全部客户的指标」在客户端路径上根本写不出来。

第 2 层比第 1 层重要：第 1 层保证「有人在检查」，第 2 层保证「想绕都绕不过去」。

## 四、Token：自签的 HMAC，不用 JWT

两套认证换出来的是同一种 token，只是 `scope` 不同。格式：

```
v1.<base64url(payload)>.<base64url(hmac_sha256(payload, AUTH_SECRET))>
```

payload 里只有四个字段：`scope`（`client` / `operator`）、`sub`（客户端是
`client_id`，内部是运营标识）、`exp`、`iat`。

⚠️ **`iat` 是「首次签发」，不是「本次签发」。** 续期时它原样保留，只推 `exp` ——
下一节那个 90 天绝对上限正是 `iat + 90 天` 算出来的，而自包含 token 里必须有个
东西记住起点。让 `iat` 担这个角色，比加第五个字段省事，代价是这句话必须写下来：
重置它一次，那条上限就形同虚设，而且不会有任何报错。

**为什么不用 JWT。** JWT 的灵活性这里一样都用不上（不需要多算法、不需要跨服务
验签、不需要第三方签发），而它的复杂度带来了真实的攻击面：`alg: none`、
HS256/RS256 混淆，都是因为「算法由 token 自己声明」这个设计。我们只有一个算法，
把它写死在代码里，那类攻击就不存在。

**这不是自创密码学。** 用的是标准库的 `hmac.new(..., hashlib.sha256)` 和
`hmac.compare_digest`（后者防时序侧信道），属于「正确使用现成原语」。真正需要小心
的是三件事，各自有测试盯着：**签名比对必须用 `compare_digest`**（`==` 会泄露信息）、
**过期必须在验签之后判**（顺序反了等于给了一个不验签的解析入口）、**payload 改一个
字节就必须验不过**。

`v1.` 前缀是给将来留的路：换算法时新旧并存一段时间，而不是让所有人同时失效。

### 有效期与续期

| | 客户端 | 内部 |
|---|---|---|
| 单次有效期 | 7 天 | 8 小时 |
| 能否续期 | 能，未过期时可换新的 | 能 |
| 绝对上限 | 90 天，之后必须重新扫码 | 无（重新登录即可） |

客户端做**滑动过期**：常看的人永远不用重扫，不活跃的自然失效。但滑动必须有绝对
上限 —— 没有上限的话一个 token 可以无限续下去，等于永久凭据，而「客户换了手机、
旧手机被卖掉」这类事没有任何办法处理。上限从**首次签发**算起，续期不重置它。

内部 token 短，因为它的权限大得多：它能导数据、能改客户。

⚠️ **自包含 token 撤销不了。** 想立刻踢掉某个客户，只能改 `AUTH_SECRET`（所有人
一起失效）或等它过期。MVP 接受这个代价 —— 换成「每次请求查一遍库」要为它引入一张
会话表和一次额外查询，而这个系统的访问量是「几个客户每天看几次」。**这条要写进
[`docs/business/`](../business/) 对应那篇**，别让下一个人以为有撤销功能。

## 五、客户端怎么登录：邀请码 → token

内部后台给某个客户生成一个邀请码，渲染成二维码/链接，客户扫了就进。

### 为什么不是严格的「一次性」

主设计文档第十节第 3 条写的是「一次性链接/二维码」。落地时改成**有效期内可多次
使用**，因为「一次性」在真实场景下会立刻失效：一个客户往往有老板和运营两个人要看，
还可能换手机、清缓存、小程序被清理 —— 每次都要运营重新生成一个，那是把成本转嫁给
了唯一不该被打扰的人（运营）。

取而代之的约束：

- 邀请码本身有**过期时间**（默认 30 天），过期后不能再换 token；
- 可以**手动作废**（内部后台一键失效），用于「这个客户不合作了」；
- 已经换出去的 token **不受作废影响**（自包含，见上节），最多再活 7 天。

邀请码是**存库**的（`invites` 表），不是自签的 —— 它需要能被作废、能被列出来看
「这个客户的码什么时候发的」，这些都要状态。它和 token 的区别正是「要不要能撤销」。

### 内部后台怎么登录：不建用户表

运营账号从环境变量读（用户名 + 密码哈希），**不建 `users` 表**。

理由是「单实例单使用者」这条已有的范围约束：为一两个人建一套用户管理（增删改、
改密码、找回密码、权限分级）是典型的范围蔓延，而它们每一个都要接口、要页面、要
测试。多人共用一个运营账号在自托管小团队里是可接受的 —— 这是**明确记下来的取舍，
不是遗漏**。

密码在 `.env` 里存**哈希**不存明文（用 `argon2` 或 `bcrypt`），生成方式写进
README。存明文的话，`.env` 一旦被谁贴进聊天窗口就是直接可用的凭据。

## 六、代码摆在哪

```
client/              uni-app 3 + Vue 3 + TS + Pinia，出小程序 / H5
admin/               Vue 3 + TS + Element Plus，内部操作台
  src/api/generated/ ← 两端各自由 OpenAPI 生成的 TS 类型，不手写、不手改

src/adpilot/
  auth/              🆕 顶层模块：token 的签发与校验
    token.py         纯函数，只依赖 config —— 不碰数据库
    password.py      运营密码的 argon2 哈希；`python -m adpilot.auth.password` 生成
  models/invite.py   🆕 邀请码
  services/invite.py 🆕 生成、兑换、作废
  api/
    deps.py          加 ClientScopeDep / OperatorDep
    auth.py          🆕 登录、续期、邀请码兑换
    invite.py        🆕 邀请码的运营侧接口（tag 用 clients，挂在客户下面）
    portal.py        🆕 客户端接口，作用域锁死（单文件，五个接口用不着建目录）
```

`auth/` 是新顶层模块，分层契约开着 `exhaustive`，**必须先在
[architecture.md](../code-rules/architecture.md) 那张图和 `pyproject.toml` 里占位**。
它放在 `rules` 同层：token 签发与校验是纯计算，够不着 `models` / `db`，所以想在里面
写一句「查一下这个 token 有没有被撤销」会被契约当场拦下 —— 那正是上面「自包含 token
不可撤销」那个决定的机器形态。

邀请码需要状态，所以它走正常的 `models` → `services` 分层，不进 `auth/`。

### 类型生成进 CI

技术选型那栏写着「自带 OpenAPI → 前端类型可生成（延续 gots 的接口契约主张）」。
这一段要把那句话变成门禁，而不是停在「可以生成」：

```
后端跑起来 → 导出 openapi.json → openapi-typescript 生成 .ts → git diff --exit-code
```

有差异就红，意味着**后端改了出参形状但没同步前端类型**。这是同仓库放代码换来的
主要好处；分仓的话这条只能靠人盯。

代价老实说清楚：CI 要装 Node，集成 job 会变慢。

> **这道门禁挪到 D10 第一件事**（2026-08-21，D9）：它要 CI 装 Node，而 D9 结束时
> 一个前端都还没有 —— 生成出来的 `.ts` 没有任何人消费，那样的门禁只是成本。

## 七、里程碑：D9–D11 装不下

主文档给 D9–D11 定的是「uni-app 客户端」，而这一篇把认证层和内部后台也放了进来。
**不假装三天做得完**，重新划一次：

| 天 | 产出 | 验收标准 |
|---|---|---|
| D9 ✅ | 认证层 + 授权作用域 + 邀请码 | 拿别人的 token 查不到我的数据，且这件事有测试盯着 |
| D10–D11 | uni-app 客户端 | 微信小程序 + H5 双端能跑，扫码进去看到看板 |
| D12 | Vue 3 内部后台 | 客户管理、导入、邀请码生成能在页面上走完 |
| D13–D14 | LLM 日报 + 诊断 | 日报有那一行人话，输出过 schema 校验 |
| D15 | README + 截图/GIF + 部署 | 陌生人 clone 能在五分钟内跑起来 |

**总盘子从 14 天变成 15 天**，多出来的是内部后台。原来的 D12–D13（LLM）顺延一天。

这个顺序不能换：**认证必须在两个前端之前**。反过来的话，前端会先按「没有认证」写
一遍，然后每个请求都要回头改 —— 而漏改的那个不会报错，只会在某天变成一条谁都能
调的接口。

## 八、明确不做

写下来防止范围蔓延，理由与主文档第七节同源：

- ❌ **不做用户管理**（注册、找回密码、角色权限）。运营账号从环境变量来，见第五节
- ❌ **不做微信授权登录**。需要企业资质和备案，开源使用者大多没有，H5 端也用不了
  （主文档第十节第 3 条已定）
- ❌ **不做 token 撤销列表**。自包含 token 的代价已经在第四节写明
- ❌ **不做客户端的写操作**。客户端全只读 —— 客户能改的东西一旦存在，「谁改的」
  就成了新问题，而这套系统连操作记录都还没做
- ❌ **不做 App 打包**。uni-app 出小程序和 H5 两端就够，App 要证书和应用商店账号，
  开源使用者拿不到
- ❌ **不做前端的端到端测试**。类型生成那道门禁 + 后端的接口测试覆盖了契约，
  而 E2E 需要起浏览器，在这个规模下维护成本高于收益
