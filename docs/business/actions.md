# 投放操作记录

**代码**：`models/action.py`（表）· `schemas/action.py`（出入参）·
`services/action.py`（登记、查询、日切换算）· `api/action.py`（路由）·
`tests/test_actions_api.py`

**范围出处**：[设计文档 §10.4](../design/2026-08-19-mvp-design.md) ·
[LLM 日报与诊断 §10](../design/2026-08-21-llm-reports.md) · 里程碑 D13

**OpenAPI tag**：`actions`

## 一句话职责

回答一个问题：**这一段时间里，人对这个账户做了什么、为什么这么做。**

**不负责**：执行任何调整（这个系统不碰广告平台的写接口，见
[设计文档第五节](../design/2026-08-19-mvp-design.md)的三条硬边界）、判断这次调整
是对是错（那是日报里 LLM 解释的事，而它只解释、不评价执行）。

**为什么它排在日报之前做**：日报「本期做了什么」那一段没有别的数据来源。这张表
空着，日报就只能靠回忆写，而回忆必然漏。

## 接口

| operationId | 路径 | 说明 |
|---|---|---|
| `recordAction` | `POST /api/ad-accounts/{id}/actions` | 登记一次投放调整 |
| `listActions` | `GET /api/ad-accounts/{id}/actions` | 该账户的操作记录，最近做的在前 |

客户端（`/api/portal/*`）**看不到这个领域** —— 客户读到的是日报里那一段，不是
原始的操作流水。

## 能读文档就够的部分

| 规则 | 一句话 |
|---|---|
| 🔴 **`reason` 必填** | 「为什么这么调」是这张表和平台变更日志的唯一区别。平台记得住「预算 500 → 800」，记不住「周末 CPM 普涨，先扛量到周一」，而后者才是日报里值钱的那句 |
| `summary` 也必填 | 一行人话，直接能进日报 |
| `kind` 是枚举 | `budget` / `bid` / `creative` / `targeting` / `status` / `other`。枚举而不是自由文本，是为了让「本周改了 3 次预算」这种句子写得出来（动作要**可数**） |
| `source` **不让传** | 手工登记的一律 `manual`。放它出去，人会随手标成「平台抓的」，于是「这条的 `reason` 可不可信」再也答不上来 |
| `performed_at` 不是登记时间 | 是操作**实际发生**的时刻（登记时刻是 `created_at`）。下班前补登记白天做的几件事，两者差几小时是常态 |
| 必须带时区 | 裸时刻会被按服务器时区解释，于是一条傍晚的调整在日报里落到前一天 |
| **未来时刻 → 422** | 落在未来的记录永远不会进任何一期日报，却看起来像是记过了 |
| `level` 默认账户级 | 「整体调了日预算」是最常见的一类。动在系列/广告组上就填对应层级 + `object_id` |
| 层级枚举与日指标**共用一套** | 两边各定义一套的话，「改了这个系列的预算」和这个系列当天的花费就对不上，而对不上那天没有任何东西会报错 |
| 列表按 `performed_at` 倒序 | 不是按登记时间。补登记的那几条录入更晚、描述的事更早，混着排读不出投放的先后 |
| **没有修改和删除** | 这张表是日报的证据链。填错了再登记一条说明，那本身也是投放过程的一部分 |

## ⛔ 必须读源码的部分

- **日报要的那个查询形态，以及它的时区换算**（`services/action.py` 的
  `window_bounds` 与 `list_in_window`）。`daily_metrics` 按**自然日**存、`actions`
  按**时刻**存，日报要把两者对到同一天上，换算必须发生在某处 —— 收口在
  `window_bounds` 这一个函数里。看签名推不出来的有三件：

  1. 出参是**半开区间**（右端是次日零点）。写成「≤ 当天 23:59:59」会漏掉那一秒
     之内的操作，而漏掉的那条不会有任何迹象；
  2. 零点按**账户时区**取。用服务器时区截，日切点附近的操作整体归到相邻那一天
     —— UTC 的 08-15 06:00 在 Anchorage 是 08-14 22:00，两期日报都不会报错；
  3. 夏令时切换日的窗口**不是 24 小时**，这是刻意接受的（理由在函数 docstring 里）。
     ⚠️ 顺带一个语言坑：拿两端相减去量窗口长度会得到 24 小时 —— 两个 aware
     datetime 的 tzinfo 相同时 Python 按朴素时间相减、不看偏移量。要量就先
     `astimezone(UTC)`。

  这三件事算错了都**不报错**，只是让某条记录出现在错误那一期日报里。

## 已知残余

- ✅ **发布日报前校验操作记录非空**已经落地（D14），写在 `services/report.py`
  的 `publish` 里。⚠️ 它校验的是**日报快照里的**那份，不是此刻这张表里的 ——
  生成时忘了登记，补登记之后要**重新生成**日报才算数（见 [日报](reports.md)）。
- 🚧 **`ActionSource.PLATFORM` 没有任何写入路径。** 它是给「接了 Ads API 之后自动
  抓变更日志」留的位置。那天的形态：自动抓来的记录**没有 `reason`**，手动登记降级
  为补充而不是被取代（[设计文档 §10.4](../design/2026-08-19-mvp-design.md)）。
- **没有 `detail` 那种结构化前后值。** 手动登记的场景下人写的就是 `summary` 那一行
  人话，多一个自由字典只会诱使人往里塞结构而没有消费者。等 `PLATFORM` 那条来源
  接进来、前后值由平台给出时再加，那时它有明确的生产者。
- ✅ **内部后台的登记界面有了**（D17）：在[账户明细](admin.md)那一屏，和录余额
  并列。⚠️ 在那之前它是一条**断链** —— 日报发布硬校验这张表当期非空，而登记只能
  调接口，于是后台走不完运营的一天。日报屏上那句「先去账户明细登记」从 D14 起就
  在指路，指了三轮，而路是 D17 才修的。
- **没有跨账户的「今天全公司做了什么」视图。** 查询形态只有「某账户 + 某区间」，
  因为日报是按账户出的。真要总览时再加。
