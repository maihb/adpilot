# 日报

**代码**：`models/report.py`（表）· `schemas/report.py`（出入参与派生指标）·
`services/report.py`（生成、修订、发布）· `api/report.py`（内部路由）·
`api/portal.py`（客户端那两个）· `tests/test_reports_api.py`

**范围出处**：[设计文档 §5](../design/2026-08-19-mvp-design.md) ·
[LLM 日报与诊断 §3–4](../design/2026-08-21-llm-reports.md) · 里程碑 D14

**OpenAPI tag**：`reports`（客户端那两个在 `portal` 下）

## 一句话职责

**把一天的投放讲清楚，然后交给人确认，再发给客户。**

**不负责**：算数字（那是 [日指标](metrics.md)）、判断要不要告警（[规则](alerts.md)）、
执行任何调整（这个系统不碰广告平台的写接口）。

日报由两部分组成，**它们的来源必须分开**：

| 部分 | 谁产生 |
|---|---|
| 数字（花费、CPA、环比） | **代码**，从 `daily_metrics` 算 |
| 那一行人话 | LLM 写初稿，**人改完才算数** |

日报的价值不在数字 —— 数字客户自己也能从平台后台导出来。价值在「成本上升是周末
CPM 普涨，未做调整，观察到周一」这句话，以及「本期做了什么」那一段。

## 接口

| operationId | 路径 | 说明 |
|---|---|---|
| `generateReport` | `POST /api/ad-accounts/{id}/reports` | 生成某一天的日报（数字在这一刻固定） |
| `listReports` | `GET /api/ad-accounts/{id}/reports` | 该账户的日报，含各状态 |
| `getReport` | `GET /api/reports/{id}` | 全文，**两版人话都给** |
| `reviseReport` | `PATCH /api/reports/{id}` | 存人工修订后的那版，并盖「人看过了」的戳 |
| `publishReport` | `POST /api/reports/{id}/publish` | 发布。**两条硬校验在这里**，且收不回来 |
| `listPortalReports` | `GET /api/portal/reports` | 客户看自己的，**只有已发布的** |
| `getPortalReport` | `GET /api/portal/reports/{id}` | 同上，全文 |

## 能读文档就够的部分

### 生命周期

```
draft ──LLM 写完──▶ pending_review ──发布──▶ published ──▶ 客户可见
  ▲                      ▲
  └ LLM 失败时停在这里    └ 人工修订之后一定到这里（无论从哪来）
```

| 规则 | 一句话 |
|---|---|
| 一个账户一天**只有一份** | 唯一键 `(account_id, stat_date)`。客户手上同一天出现两份日报，比数字错了更让人不安 |
| 未发布的可以**重新生成** | 覆盖数字和模型原文，**并清掉人工修订** —— 数字变了，基于旧数字写的那段话未必还成立 |
| 已发布的**既不能改也不能重新生成** | 409。要更正就在新一期里说明 |
| 🔴 **LLM 挂了不影响生成** | 状态停在 `draft`、人话为空，人自己写。数字部分是确定性的，不该被模型的可用性绑架 |
| 没配 LLM 是**正常状态** | 同上那条路径。陌生人 clone 下来没有 API key，日报照样出得来 |

### 🔴 两条硬校验（都在服务层，不是 UI 提示）

| 校验 | 为什么 |
|---|---|
| **必须经人工修订** | 模型可能在散文里写「成本上升了 40%」而实际是 24%，而**没有任何机器判定拦得住**（正则抽数字会被「四成」绕过去）。人是唯一的防线。判据是 `reviewed_at` 非空 —— 人工确认要显式留痕，不从「文字有没有内容」反推 |
| **操作记录不能为空** | 「本期做了什么」是交付价值所在，动作要可数（[设计 §10.4](../design/2026-08-19-mvp-design.md)）。一份说不出做了什么的日报，就是一张客户自己也能导出来的表 |

校验的是**快照里的**操作记录，不是此刻 `actions` 表里的：日报正文里写的和发布时
校验的必须是同一份，否则会出现「校验通过了，但正文那段是空的」。生成时忘了登记，
就补登记再**重新生成**。

### 🔴 快照：日报不是视图

**数字在生成那一刻固定，此后不随平台回填变化**（[glossary](glossary.md) 的「日报
快照」）。反过来做的后果不是「数字更准」，是**客户上周收到的日报今天再打开数字变
了** —— 而「报表数字会自己改」解释不清，它会连带摧毁对全部数字的信任。

⚠️ 固定发生在**生成**那一刻，不是发布那一刻：人审的必须就是发出去的那份。

操作记录和告警摘要也是快照（存的是当时那几条文字的副本）—— 删掉一条操作记录不该
让已发布的日报内容跟着变。

### 两版人话都存

| 字段 | 谁写的 | 能不能改 |
|---|---|---|
| `llm_narrative` | 模型 | 🔴 **永不修改** |
| `narrative` | 人 | 发布前随便改 |

要能回答「这句话是模型写的还是人改的」—— 那是评估这套系统值不值得信的唯一依据
（[设计 §6](../design/2026-08-19-mvp-design.md)）。**客户看到的是 `narrative`**，
客户端出参里根本没有 `llm_narrative` 这个字段（有门禁盯着）。

两版**同构**（`summary` + `highlights` + `next_steps`），否则「哪一段是谁写的」
没法逐段回答。这两个类刻意不复用（LLM 层的契约跟着提示词演进，对外 API 的要稳定），
所以同构由 `tests/test_reports_api.py` 的一条测试盯着。

### 数字口径

| 规则 | 一句话 |
|---|---|
| `stat_date` 是**账户时区**下的自然日 | 出参带着 `timezone`，前端要把这句口径显示出来。不注明的话客户拿自己后台的数字来对永远差一截 |
| 对照期是**上周同日** | 抵消星期几效应（[glossary](glossary.md) 的「周同比」），和异动规则同一个口径 |
| 🔴 对照期没数据 → **三项全空** | 环比整段不显示。补一个 0 会算出「上升了 100%」这种凭空的百分比，而模型会照着它写进日报 |
| 派生指标**不存库** | CPA / CTR / CPM / ROAS 由出参现算，和看板共用同一份公式（`schemas/daily_metric.py` 的 `DerivedMetrics`）。存下来就等于把公式复制进数据库 |
| 币种和时区**在日报行上存一份** | 账户的这两项可以被改，改了之后已发布的日报仍要按当时的口径解释 |
| 金额和比率是**字符串** | 前端不要用浮点解析（[conventions](../code-rules/conventions.md)） |

### LLM 看得到什么

只有 `services/report.py` 的 `_llm_input` 交出去的那些：账户名、日期、口径、**格式
化好的**几个数字、告警摘要、操作记录。**没有账户 ID、客户 ID、内部主键** —— 那些
会跟着提示词发到第三方服务器上，而它们对措辞没有任何帮助。

模型的输出契约里**一个数字字段都没有**（[LLM 层](llm.md)），所以「模型把 CPA 编成
另一个值」在结构上不可能。它仍然可能在散文里编一个百分比 —— 那就是上面那道人工
闸门存在的原因。

## ⛔ 必须读源码的部分

- **`services/report.py` 分成的那两段**（`_fill_facts` / `_write_narrative`）。中间
  那条缝是「LLM 失败不阻塞」的实现：第 1 段全是确定性代码并且已经 flush 进库，
  第 2 段失败了也只是让状态停在 `draft`。看签名推不出来的是**顺序**：先落库再调
  模型，反过来就变成「模型挂了整份日报都没了」。

- **重新生成会清掉人工修订**（`_fill_facts` 末尾那几行）。它看起来像是「顺手重置
  一下」，其实是刻意的：数字变了之后，基于旧数字写的那段话留着比丢掉更危险 ——
  它会被当成已经审过的内容直接发出去。

- **`api/portal.py` 的 `_to_portal_report` 为什么是手写的**，不用
  `model_validate`。显式构造是为了让**丢掉哪些字段**这件事在代码里看得见
  （`llm_narrative`、`status`）。自动映射的话，哪天给模型原文换个字段名，它就悄悄
  跟着下发了。

## 已知残余

- ✅ **两侧的界面都有了**（D14）：运营在 [内部操作台](admin.md) 里生成、修订、
  发布（发布要二次确认），客户在 [客户端界面](client-app.md) 里看已发布的那份。
- 🚧 **不自动生成。** 没有定时任务，日报要人点一下（或者调接口）。挂进
  `beat_schedule` 是自然的下一步，但那要先决定「几点算一天结束」——而那取决于
  账户时区，每个账户还不一样。
- **不做周报 / 月报。** 日报的口径先跑通；周期汇总有它自己的坑（`reach` 跨天不可
  加，见 [glossary](glossary.md)）。
- **不做重述。** 数字后来修正了，在新一期日报里说明，不动老的那份。
- **没有「发给客户」这个动作。** 发布之后客户端能看到，但不会主动推送给他 ——
  推送的限制见 [客户自助端](portal.md) 的残余。
