# 术语与口径

**这一篇是计算口径的真相源。** 规则引擎、日报、接口出参、前端看板都按这里的定义算，
谁也不许在自己那一层重新定义一遍 —— 同一个 CPA 出现两个值，整套输出的可信度就没了。

> **标了「⚠️ 待定」的是实现时才能定死的参数。** 定下来的当天回来把值填进这里，
> 并在代码里指向本文件。

---

## 实体

| 术语 | 是什么 | 不是什么 |
|---|---|---|
| **客户** client | 投放服务的对象，一个商家 | **不是租户**。本项目单实例单使用者，多客户是业务概念，不做隔离（[设计文档第七节](../design/2026-08-19-mvp-design.md)） |
| **广告账户** ad_account | 平台侧的投放账户，归属某个客户；带平台、币种、**时区** | 不是登录账号 |
| **层级** level | 归一化后的四级：`account` / `campaign` / `adgroup` / `ad` | 平台叫法不统一（Meta 的 ad set、TikTok 的 ad group），**归一化时一律映射到 `adgroup`** |
| **日指标** daily_metrics | 某账户某层级某对象在某个自然日的归一化指标 | 不是平台原始行 —— 原始行在 Mongo 的 `raw_reports` 里 |
| **操作记录** action | 人做了什么：改预算、换素材、开关计划，**含「为什么这么调」** | 不是系统日志 |
| **日报** report | 发给客户的那一份：数字 + 环比 + 做了什么 + 一句人话结论 | 不是数据的实时视图，理由见下面「日报快照」 |
| **余额** balance | 账户可用余额的快照 | 不是消耗 |

---

## 时间口径

**`stat_date` 一律是「广告账户时区下的自然日」**，账户时区记在 `ad_accounts` 上。

广告账户时区、店铺时区、看报表的人所在时区**可以是三个不同的值**，日切点因此能差
出好几个小时。所以：

- 跨账户汇总时**不要**把不同时区的 `stat_date` 当成同一天再相加 —— 能加，但要知道
  加的是什么，并在日报里注明
- **日报必须写明口径**（哪个时区的哪一天）。不写的话，客户拿他自己后台的数字来对，
  永远差一截，而那是解释不清的差异

---

## 指标

分母为 0 时**一律返回「无定义」（`null`），不返回 0，也不返回无穷**。写 0 会让
「今天没有转化」和「今天 CPA 是 0 元」变成同一个显示值，而这两件事在日报里天差地别。

| 指标 | 公式 | 坑 |
|---|---|---|
| **spend** 花费 | 平台原值 | **账户币种**，不是人民币。跨账户汇总前必须先说清楚要不要换算 |
| **impressions** 展示 | 平台原值 | 可加 |
| **clicks** 点击 | 平台原值 | 平台有「全部点击」和「链接点击」两种口径，**归一化时固定取链接点击**并在 `raw_reports` 里留着原值 |
| **conversions** 转化 | 平台原值 | ⚠️ **取哪个转化事件必须显式配置**（购买？加购？表单？），不配置就没有可比性。**当前实现**：取导出文件里的 `Results` / `转化数` 列，也就是导出时在后台选定的那个事件 —— 这个假设收口在 `services/field_maps.py` 的 `CONVERSIONS_COLUMNS`，口径定下来那天只改那一处 |
| **revenue** 转化价值 | 平台原值 | 同上，且受归因窗口影响 |
| **CPM** 千次展示成本 | `spend / impressions * 1000` | |
| **CPC** 单次点击成本 | `spend / clicks` | |
| **CTR** 点击率 | `clicks / impressions` | 存小数不存百分数，展示时再乘 100 |
| **CPA** 单次转化成本 | `spend / conversions` | 最常被问的数，也最容易两边算不一样 |
| **ROAS** 广告支出回报 | `revenue / spend` | |
| **reach** 触达人数 | 平台原值 | 🔴 **跨天不可加**，见下 |
| **frequency** 频次 | `impressions / reach` | 🔴 **跨天不可加**，见下 |

### 🔴 reach 和 frequency 不能跨天相加

同一个人今天和明天都被触达，两天的 reach 相加会把他算两次，得到的数字**没有意义**
（不是「不够精确」，是错的）。频次由 reach 算出来，同理。

所以：**周期性汇总的 reach / frequency 必须向平台单独请求那个周期的数值**，不能拿
日数据加出来。在这之前，日报里的频次只写「当日频次」。

## 数据会变：回填与重述

平台的历史数据**在若干天内还会变**：归因回传、无效流量剔除、汇率重算。同一个
`(账户, 日期)` 今天拉是一个数，三天后拉是另一个数。这不是 bug。

三条应对，缺一条就会出问题：

1. **拉取要回溯。** 每次同步不只拉昨天，要往回拉 ⚠️ **N 天（待定，倾向 7）**。
2. **`daily_metrics` 按唯一键 upsert**（`account_id, level, object_id, stat_date`），
   同一天重导是覆盖不是追加。**没有这个唯一键，导两次就是双倍花费。**
3. **`raw_reports` 每次都新增一条快照**，永不更新 —— 「当时这个数到底是多少」只能
   从这里查。这正是双库边界存在的理由。

### 日报快照

**日报一旦生成就固定住当时的数字，不随后续回填变化。**

反过来做（日报实时算）会导致：客户上周收到的日报，今天再打开数字变了。哪怕新数字
更准确，这也会直接摧毁信任 —— 而「报表数字会自己改」是解释不清的。

数字确实变了且值得说明时，**发新的一份并注明重述**，不动老的那份。

---

## 归因差异：不要试图对齐

平台报表的转化数和客户自己后台的订单数**永远对不上**，而且**两个平台的转化数相加
大于实际订单数是正常现象**。原因固定是那几个：

- 归因窗口不同（点击后 7 天 vs 当日）
- 浏览归因（看到没点也算）
- 跨设备归因
- 两个平台对同一笔订单各自邀功

**处理方式是把两个数字都列出来 + 附固定的差异说明**，而不是想办法让它们一致。
让它们一致的唯一办法是篡改其中一个。

## 规则（确定性计算，不经 LLM）

这几条是[设计文档第五节](../design/2026-08-19-mvp-design.md)那条边界的落点：
**能用规则算的绝不用 LLM。** 全部实现为 `rules/` 下的纯函数，参数化测试覆盖。

### 余额可撑天数

```
days_left = available_balance / avg_daily_spend
```

- `avg_daily_spend` 取**近 N 天**的日均消耗。⚠️ **N 待定，当前实现取 7**（盖住一个
  完整的周内/周末周期；取 3 会让「周一算出来的日均」系统性偏低）。收口在
  `rules/balance.py` 的 `LOOKBACK_DAYS`
- 分母为 0（近期没花钱）→ **无定义**，不告警，不显示为「无限」
- 低于**阈值**触发告警，判定含等号。⚠️ **阈值待定，当前实现取 3 天**（「发现 →
  通知客户 → 客户走完充值流程」的现实耗时）。收口在 `ALERT_THRESHOLD_DAYS`
- 🔴 **日均的分母是「区间内真有数据的天数」，不是 N。** 某天没导入 ≠ 那天没花钱；
  用 N 当分母会让日均被系统性拉低 → 可撑天数被高估 → **该告警的账户不告警**。
  反过来最坏只是多报一次告警，那个方向的代价小得多
- **窗口不含今天**（今天的数据还没跑完），且按**账户时区**截 —— 用服务器时区会在
  日切点附近整体差一天
- **两个输出各有精度**：天数保留 1 位（「还能撑 2.3333333 天」没人需要），日均消耗
  是金额、保留 4 位（对齐 `numeric(20,4)`）。都在 `rules/balance.py` 的产地量化 ——
  日均有两个出口（告警里的人话、`detail` JSONB），留给调用方量化必漏一个
- 🔴 **只取一个层级的花费**（`account` → `campaign` → `adgroup` → `ad`，取有数据的
  最高层级）。同一天既有账户级又有系列级数据时全加起来就是双倍花费，日均翻倍、
  可撑天数腰斩，凭空多出一条告警

完整规则与边界见[余额与告警](balances.md)。

**为什么这条排在最前面**：预充值账户余额归零，广告是**停**不是降速。停一次，3–5 天
的学习期白跑，重开还要再等 3–5 天 —— 代价远大于「少花一天钱」。

### 库存可撑天数

```
stock_days_left = stock_qty / avg_daily_sales
```

口径与上面一致（同样的 N、同样的「分母为 0 即无定义」）。主推款断货而广告还在跑，
学习期同样作废。

### 指标异动

**规则只负责「涨了 40%」这个判定，「大概率是素材疲劳，建议换素材」是 LLM 那一层的
事** —— 两者不能混在一起写。

- **当前实现只做周同比**（昨天 vs 上周同一天），不做日环比。理由：星期几效应是这个
  领域最强的周期性噪音源，日环比会在每个周六和周一各制造一批假告警 —— 而设计文档
  举的那个日报例子原文就是「成本上升是周末 CPM 普涨，未做调整」。代价是需要 8 天
  数据，新账户前一周判不了（那时不判，而不是拿凑合的基线硬判）
- 超出 ⚠️ **阈值（待定，当前实现取 ±40%）** 即标记，判定含等号。收口在
  `rules/anomaly.py` 的 `CHANGE_THRESHOLD`
- 只看 `spend` 和 `cpa` 两个指标。**花费涨跌都报**（暴涨可能是出价失控，暴跌可能是
  被拒审或预算见底），**CPA 只报涨** —— 成本下降是好消息，塞进告警清单只会稀释真正
  要处理的那几条
- 噪音门槛 ⚠️ **（待定，当前实现取 10，账户币种）**：**两天都低于**它才跳过。小额
  消耗的比率毫无意义（花 1 块变成 2 块就是 +100%），但「昨天花 500、上周同日花 2 块」
  正是最该被看见的那种跳变，所以用 and 不用 or
- 基线为 0 或缺任一边的值 → **不判**。「从 0 涨到 100」在数学上不是「涨了百分之几」

完整规则与状态机见[告警与巡检](alerts.md)。

## LLM 只做三件事

边界的完整论述在[设计文档第五节](../design/2026-08-19-mvp-design.md)，这里只放
一句话版本，方便写代码时随手对照：

| 能做 | 绝不做 |
|---|---|
| 把已经算好的数字写成人话 | 自己算数字 |
| 解释异动可能的原因、给建议 | 判定有没有异动 |
| 回答基于自有 SOP 的问题 | 改预算、开关广告、调出价 |

**输出一律过 Pydantic 校验，不合格就重试**，裸文本永远不进数据库、不发给客户。
每次调用记 token 数与预估成本。
