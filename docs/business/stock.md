# 库存与断货预警

**代码**：`rules/stock.py`（可撑天数与日均推算，**纯函数**）·
`providers/stock_csv.py`（库存表解析）· `services/product.py`（导入、查询、把数据
喂给规则）· `models/product.py`（两张表）· `schemas/product.py` · `api/product.py`
（路由）· `tests/test_rules_stock.py` `tests/test_stock_csv.py`
`tests/test_products_api.py`

**范围出处**：[设计文档 §2.3](../design/2026-08-19-mvp-design.md) ·
[库存断货设计](../design/2026-08-21-stock-alerts.md) · 里程碑 D16

> 告警怎么去重、要不要重复提醒，在[告警与巡检](alerts.md)那一篇 —— 所有状态机
> 归一处。这一篇只讲库存本身。

**OpenAPI tag**：`products`

## 一句话职责

回答一个问题：**这个款还能卖几天。**

**不负责**：补货（那是客户和供应商之间的事）、销量本身（我们没有订单数据，见下）、
「哪个广告在推这个款」（[明确不做](#明确不做)）。

**为什么值得做**：广告刚跑起来、主推款断货，学习期同样作废 —— 代价和余额归零一样。
而[设计文档](../design/2026-08-19-mvp-design.md)把难点说得很直白：**库存数据在店铺
后台、投放数据在广告后台，两边没人对**。这一段解决的就是「把两个后台的数摆到一起」。

## 接口

| operationId | 路径 | 说明 |
|---|---|---|
| `importStock` | `POST /api/clients/{id}/stock-imports` | 导一份库存表（CSV） |
| `listProducts` | `GET /api/clients/{id}/products` | 这个客户的商品 |
| `listStockRunway` | `GET /api/clients/{id}/stock-runway` | 每个在售商品还能撑几天 |

断货告警本身在 `GET /api/alerts`（`kind = stock_low`），和其余告警同一个清单。

## 能读文档就够的部分

### 数据挂在哪

| 规则 | 一句话 |
|---|---|
| 🔴 **商品挂在客户上，不挂账户** | 一个客户可以同时投 Meta 和 TikTok，推的是**同一批货**。挂在账户上就有两份库存记录，补货时要改两处，漏一处就是一条假告警 |
| 唯一键是 `(client_id, sku)` | 两家店各有一个 `A-001` 完全正常，所以不同客户之间不互相约束 |
| 于是**告警也是客户级的** | `alerts.account_id` 为 `NULL`。这是 D16 动 `alerts` 表的全部原因，取舍见[设计第三节](../design/2026-08-21-stock-alerts.md) |
| 快照**不走 Mongo**，直接进 PG | 表的形状由我们自己定（一份导入模板），没有平台在改它，也就没有「三个月后要查当时是什么口径」这个问题。⚠️ 接了店铺 API 之后这条要重看 |

### 怎么导

| 规则 | 一句话 |
|---|---|
| **只有批量 CSV，没有单条录入** | 和余额刚好相反：余额一个账户一个数，库存一个客户几十上百个 SKU |
| 列名自动认 | 商品编码 / 库存必需，商品名 / 日均销量可选。认不出必填列会**把表头列出来**，不猜 |
| **重传是覆盖，不是 409** | 也和余额相反：库存是文件上传，重传同一份（网络断了、少了一列重来）是常态而不是误操作 |
| 🔴 **文件里没有的 SKU 一律不动** | 部分导出是常态（只导主推款、只导某个分类）。把「这次没导」读成「卖光了」，会让每次部分导入都炸出一屏假告警 |
| 商品是 upsert，快照是 append | 名字跟着文件更新（改名是常事），但**空名字不覆盖已有的** |
| `captured_at` 不是上传时间 | 是「这份库存属于哪一刻」。必须带时区 —— 推算日均按**时刻差**算，偏几小时会直接落进那个除法 |
| 同一份文件里 SKU 重复 → 报错 | 按仓库分行（该相加）和复制粘贴的重复（该去重）得出的库存差一倍，而两者长得一模一样。**不猜** |
| 负库存夹到 0 | 「超卖 3 件」和「卖光了」要采取的行动完全一样，而放它进来会让可撑天数变成负数 |

### 怎么算

| 规则 | 一句话 |
|---|---|
| 公式 | `stock_days_left = stock_qty / avg_daily_sales`，口径的真相源是 [glossary](glossary.md#库存可撑天数) |
| **分母有两个来源** | ①导出文件自带的「日均销量」列 —— **永远优先**；②没有那一列时，**从快照序列推** |
| 推算 = 相邻两次快照的库存降幅 ÷ 那些段覆盖的天数 | 一句话版本：**库存掉了多少，就是卖了多少** |
| 库存**没动**的那一段：销量记 0，天数照算 | 「三天没卖出去」是可信的信息，不是缺数据 —— 与余额那条「暂停投放的日子算进分母」是同一条规矩 |
| 库存**上升**的那一段：整个跳过 | 补货了。「补了 100 卖了 20」和「补了 80 卖了 0」在两个端点上看**完全一样** |
| 取最近 **8 条**快照，不按天窗口截 | ⚠️ 待定参数（`LOOKBACK_POINTS`）。库存快照的密度由**人的导入节奏**决定，按天截会让「一周传一次」的客户永远算不出日均 —— 而导得少的正是盯得少的那批 |
| 跨度超过 **30 天**的相邻两点不算 | ⚠️ 待定参数（`MAX_SPAN_DAYS`）。三个月前传过一次、今天又传一次，中间发生过什么完全不知道，算出来是个**精确的胡话** |
| 阈值 **7 天** | ⚠️ 待定参数（`ALERT_THRESHOLD_DAYS`），判定**含等号**。**不是余额那个 3 天** —— 充值是分钟级的动作，补货是周级的 |
| 天数保留 1 位，日均保留 4 位 | 都在 `rules/stock.py` 的产地量化。日均有两个出口（告警里的人话、`detail` JSONB），留给调用方量化必漏一个 |

### 什么时候告警

| 情况 | 结果 |
|---|---|
| `days_left ≤ 7` | **告警**。等号要算上 —— 阈值的语义是「留给人补货的时间」 |
| 库存 ≤ 0 | **告警**，`days_left = 0`。广告此刻正在给一个买不到的链接引流 |
| 日均算不出来（只有一条快照、或者中间只有补货） | `days_left = null`，**不告警**。出参里 `sales_source = none` |
| 近期没动销（日均 = 0） | 同上，**不告警**。没有消耗就不会断货 |
| 从没导过库存 | 这个商品**根本不出现**在清单里。没导过 ≠ 库存是 0 |
| 商品 `is_active = false` | 下架的款不巡检 |
| 🔴 客户**一个在投账户都没有** | 整个跳过。断货告警的意义是「广告还在跑，货没了」；广告没在跑时它只是一条店铺经营信息 |

`null` 一律表示**无定义**，不是 0 —— 与 glossary 里「分母为 0 返回 null」是同一条
规矩。⚠️ 但这里有个额外的区分：**`avg_daily_sales` 为 `null` 是「算不出来」，为
`0` 是「真的没卖」。** 前者要人去补一次导入，后者不用管，出参和界面都照直区分。

## ⛔ 必须读源码的部分

- **日均来源的优先级在 `services/product.py` 的 `_alert()`，不在规则层。** 规则只
  收算好的数字，「这个数从哪来」是查库这一层才知道的事。看规则的签名推不出来：
  `runway()` 收一个 `Decimal | None`，谁给的它不关心。

- **`sales_source` 为什么必须回出去**（同一个函数）。推算出来的日均建立在「中间
  没补过货」这个假设上。不回这个字段的话，一个刚补过货的款会显示成即将断货，而
  页面上没有任何线索指向原因 —— 那是最难解释的一类错误。

- **巡检的入口是「有在投账户的客户」，用的是 `EXISTS` 不是 `JOIN`**
  （`services/product.py` 的 `alerts()`）。JOIN 会让有三个在投账户的客户出现三次，
  然后它的每个商品被算三遍。

- **对账那一趟遍历的是「被巡检过的客户」，不是「有断货商品的客户」**
  （`services/alert.py` 的 `sweep()`）。后者会让补货之后那条告警永远留在清单上 ——
  它不再出现在 findings 里，而「不再出现」恰恰是对账要看见的东西。

- 🔴 **客户级告警需要第二个部分唯一索引**（`models/alert.py`）。PostgreSQL 的
  唯一索引里 **NULL 不等于 NULL**，所以既有那个 `(account_id, kind, subject)` 索引
  对 `account_id IS NULL` 的行形同虚设 —— 少了专管客户级那一半的索引，巡检每小时
  新开一条一模一样的断货告警，一天二十四条，而每一条看起来都对。

## 明确不做

- ❌ **商品与广告系列的映射。** 「哪个广告在推这个断货的 SKU」要一张人手工维护的
  对照表，而它会立刻腐化（换素材、改系列名、一个系列推多个款）。告警说清「哪个
  客户的哪个 SKU 快断了」，剩下的判断交给人。
- ❌ **日报里不加库存段。** 日报的数字口径已经固定（快照结构、两版人话、LLM 输出
  契约），为库存加一段要同时动这四处，而库存告警已经在告警清单和客户端看得到。
- ❌ **不接店铺 API。** 与不接 Ads API 同一个理由，且更甚 —— 店铺侧的形态比广告
  平台更碎（自建站、SaaS、ERP 各一套）。
- ❌ **不做库存趋势图。** 快照都在，等有人真的要看再说。

## 已知残余

- ⚠️ **三个参数都还没有业务定论**（阈值 7 天、回看 8 条、最大跨度 30 天）。定下来
  的当天只改 `rules/stock.py` 的三个常量，并回 [glossary](glossary.md) 填值。
- **推算的日均在补货频繁的品上会偏低。** 每一段补货都被整个跳过，如果一个款几乎
  每次导入之间都补货，可用的段就所剩无几 —— 极端情况下退化成「算不出来」。那时
  正确的做法是让导出带上销量列，而不是去放宽那条跳过规则。
- **没有「安全库存」的概念。** 现在只有一个全局阈值，而不同品的补货周期差得很远
  （现货 vs 定制）。真要做，那是 `products` 上加一列覆盖 `ALERT_THRESHOLD_DAYS`。
- **导入是同步的。** 几百个 SKU 的文件在请求里解析完就返回，和报表导入的第一段
  一样 —— 解析失败要当场说。上万 SKU 的店铺会开始感觉到慢，那时该走对象存储 +
  任务队列，而不是放宽上传上限。
- **商品没有停用接口。** `is_active` 有列、巡检也认它，但还没有改它的路由 ——
  下架的款目前只能靠「不再出现在导入文件里」自然沉底，而那不影响告警（它的库存
  快照还在，仍会被算）。
