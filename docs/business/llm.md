# LLM 层

**代码**：`llm/`（适配器、契约、提示词、重试）· `services/llm.py`（闸门与记账）·
`models/llm_call.py`（调用日志与成本）· `tests/test_llm.py`

**范围出处**：[设计文档 §5](../design/2026-08-19-mvp-design.md)（三条硬边界）·
[LLM 日报与诊断设计](../design/2026-08-21-llm-reports.md) · 里程碑 D13–D14

**OpenAPI tag**：无 —— 这一层没有自己的对外接口，它由日报和诊断调用。

## 一句话职责

**把结构化输入变成结构化输出，然后把这次调用的账记上。** 别的什么都不做。

**不负责**：判断（能用规则算的一律写成规则）、计算（日报里的数字全部来自
`daily_metrics`）、执行（这个系统不碰广告平台的写接口）、决定要不要调用（那是日报
和诊断各自的编排）。

## 三条硬边界，以及它们各自被什么拦着

| 边界 | 谁在拦 | 拦不住的时候会怎样 |
|---|---|---|
| **LLM 不碰钱、不执行** | 分层契约（`pyproject.toml`）：`llm` 压在 `models`/`schemas`/`services`/`db` **之下**，写一句 `select(...)` 或调一个业务函数会被 `lint-imports` 当场拦下 | —— 拦得住，这是机器判定 |
| **数字不由 LLM 产生** | 输出契约里**只有文字字段**（`llm/contracts.py`），加一个数字字段会被 `tests/test_llm.py` 的门禁拦下 | —— 拦得住，这是机器判定 |
| **散文里不许编数字** | 🔴 **没有机器拦得住**。正则抽数字会被「四成」「近一半」绕过去 | 日报里写「上升了 40%」而实际 24%。防线是**人工修订**，见[日报](../design/2026-08-21-llm-reports.md#三-数字不由-llm-产生) |

第三条写在这里，是为了不假装它已经被管住。

## 能读文档就够的部分

| 规则 | 一句话 |
|---|---|
| 只做 **OpenAI 兼容**一种适配器 | Claude 与 Gemini 都有兼容端点，原生适配器的增量只是它们特有的功能，而写日报用不到（[设计 §6](../design/2026-08-21-llm-reports.md)）。`LLMProvider` 接口留着，这是预留不是省略 |
| 换供应商改**三个环境变量** | `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`。DeepSeek、Kimi、通义、本地 Ollama / vLLM 都接得上 |
| **没配 LLM 是正常状态** | 日报照样生成，人话字段留空并标注「未生成」。数字部分是确定性的，不该被模型的可用性绑架 |
| `response_format` 只用 `json_object` | 严格模式（`json_schema`）是 OpenAI 自家扩展，兼容端点支持得参差不齐 —— 用了它，换一家可能直接 400。目标形状靠提示词里那份 Schema 传达，出来的一律过 Pydantic 校验 |
| 输出不合格 → **重试一次** | 模型偶尔跑偏，再问一次多半就对了。连着两次不合格说明是提示词或 schema 的问题，重试一百次也没用 |
| 供应商挂了 → **不重试** | 日报跑在 Celery 任务里，退避重试是那一层的事。在这里再叠一层只会让一次外网抖动变成几分钟的阻塞 |
| **成功和失败都记账** | 失败的那几次一样烧了 token。不记就等于账目里凭空少一笔，而少的恰好是模型表现最差的那些次 |
| 🔴 **不记请求与响应正文** | 提示词里有客户的花费数字，而这张表谁都可能导出来。失败只记**异常类名**，不记消息（消息里会带 URL 或原样回显的请求） |
| token 数与成本可空 | `NULL` = 「不知道」，不是 0（「免费」）。部分端点不回 `usage`；没配单价就不估成本 |
| 成本精度是 `numeric(20,8)` | 比别处的金额更细：单价按「每百万 token」计，一次日报大约 0.0002，4 位小数会把小额系统性舍成 0 |
| 每天有**调用次数上限** | 默认 200（`LLM_DAILY_CALL_LIMIT`），超了返回 429。不是省钱，是防一个写错的循环在夜里把额度跑光 —— 自托管意味着花的是你自己的钱 |
| 额度按 **UTC 自然日**算 | 这个计数不属于任何账户，而额度是整个实例的闸门。挑一个账户的时区去截，「今天」的含义会取决于哪个账户先跑 |
| 🔴 **提示词改了就要升版本号** | 提示词是代码里的常量，版本号跟着每次调用落进 `llm_calls.prompt_version`。没有它，三个月后没法把「这份日报」和「当时那版口径」对上 |
| **CI 里一次真实调用都不发** | 那会让构建依赖外部服务和一把 API key，而它验不了本项目自己的逻辑。测试用 `llm/fake.py` |

## ⛔ 必须读源码的部分

- **`services/llm.py` 的 `run` 为什么不抛异常**。失败时它返回 `output=None` 而不是
  抛 —— 因为**失败也要记账**，而记账是一条 INSERT：让异常冒到 `api/` 层的话，
  `session_scope` 会回滚整个事务，刚写下的账跟着没了。于是「烧了 token 却查不到
  记录」，正是这张表最不该有的漏洞。看签名推不出这个理由，而「顺手改成抛异常」
  看起来完全合理。

- **`llm/__init__.py` 的模块 docstring** 是这一层边界的真相源：它够不着哪几层、
  为什么那是「LLM 只解释不决策」的机器形态、以及哪一条**保证不了**。改这一层之前
  先读它。

- **提示词版本号那条门禁怎么工作**（`tests/test_llm.py` 末尾）。它扫源码算指纹，
  改了正文不改版本号就红。被它拦到时**不要直接更新指纹** —— 先把版本号加一，
  那才是它想让你做的事。

## 已知残余

- 🚧 **日报与诊断本身是 D14**。这一层现在只有测试在调用它，没有业务入口。
- **没有成本查询接口。** 「这个月花了多少」现在要自己查 `llm_calls`。加一个汇总
  接口是自然的下一步，但它不在 D13 的验收标准里，而没有真实用量之前也定不好该按
  什么维度汇总（按天？按客户？按用途？）。
- **额度用光只记日志、不进 `alerts` 表。** 设计文档原本写「记一条告警」，落地时
  改了：`alerts` 的每一行都挂在一个广告账户上（`account_id` 非空，去重键也带着
  它），而「实例的额度用光了」是系统级的事，塞进去要么造一条挂在随机账户上的假
  告警，要么把那张表的模型改成「有时挂账户、有时不挂」。代价大于收益 —— 调用方
  拿到的是 429，日志里有 `llm_daily_quota_exceeded`。
- **不做 RAG 知识库问答**（设计文档第五节列了它）。它要一个全新的数据域（语料
  导入、切分、向量库），接口不预留 —— 等真要做时它的形状会和现在想的不一样。
- **不做多模型对比 / 投票、不做流式输出、不做周报月报**，理由见
  [设计 §9](../design/2026-08-21-llm-reports.md)。
