# 余额与告警

**代码**：`rules/balance.py`（可撑天数与阈值判定，**纯函数**）·
`services/balance.py`（录入、查询、把数据喂给规则）· `models/balance.py`（表）·
`schemas/balance.py` · `api/balance.py`（路由）· `tests/test_rules_balance.py`
`tests/test_balances_api.py`

**范围出处**：[设计文档 §2.2](../design/2026-08-19-mvp-design.md) · 里程碑 D7

> 跨账户的余额清单（`GET /api/alerts/balances`）和「谁去看、要不要重复提醒」都在
> [告警与巡检](alerts.md)那一篇 —— 所有 `/alerts*` 归一处。这一篇只讲余额本身。

**OpenAPI tag**：`balances`

## 一句话职责

回答一个问题：**这个账户的钱还能烧几天。**

**不负责**：充值（那是客户和平台之间的事）、通知（谁去看、要不要重复提醒都在
[告警与巡检](alerts.md)）、[库存](stock.md)与指标异动那两条规则（同属 `rules/`，
各有各的一篇）。

**为什么这条排在所有规则最前面**：TikTok 预充模式下余额归零，广告是**停**不是
降速。停一次，3–5 天的学习期白跑，重开还要再等 3–5 天 —— 代价远大于「少花一天钱」。
这也是[设计文档](../design/2026-08-19-mvp-design.md)里说的「MVP 第一个真正有用的
功能」。

## 能读文档就够的部分

### 数据从哪来

| 规则 | 一句话 |
|---|---|
| **只能手工录入** | 预充余额在平台后台的账户页，导出的报表里没有这一列，而 MVP 不接 Ads API。接了 API 之后这里降级成补充手段，接口形状不变 |
| **币种不让传** | 取账户的。传一个进来早晚会出现「账户 USD、余额录成 CNY」的快照，而算出来的天数看着完全正常 |
| `captured_at` 不是录入时间 | 是**这个余额属于哪一刻**。人可能今天补录昨天看到的数，算的时候信快照自己说的时刻 |
| 必须带时区 | 裸时刻会被当成服务器时区，而服务器时区和账户时区常常不是一回事，于是悄悄偏几小时 |
| 余额允许 0、不许负 | 0 是真花光了；负数一定是填错了 |
| **只增不改** | 录第二条是第二行。「上周五还剩多少」是个会被回头追问的问题，覆盖掉就再也答不上来 |
| 同一 (账户, 时刻) 重复 → 409 | 挡的是「点了两次提交」 |

### 怎么算

| 规则 | 一句话 |
|---|---|
| 公式 | `days_left = available / avg_daily_spend`，口径的真相源是 [glossary](glossary.md) |
| 回看 **7 天** | ⚠️ 待定参数，当前取 7 —— 盖住一个完整的周内/周末周期。收口在 `rules/balance.py` 的 `LOOKBACK_DAYS` |
| 阈值 **3 天** | ⚠️ 待定参数，当前取 3 —— 「发现 → 通知客户 → 客户走完充值流程」的现实耗时。收口在 `ALERT_THRESHOLD_DAYS` |
| **窗口不含今天** | 今天的数据还没跑完（多半也没导），算进去会把日均拉低 → 该告警的不告警 |
| 窗口按**账户时区**截 | `stat_date` 的口径就是账户时区下的自然日，用服务器时区去截会在日切点附近整体差一天 |
| 🔴 **分母是「有数据的天数」，不是 7** | 某天没导入 ≠ 那天没花钱。用 7 会让日均被系统性拉低、可撑天数被高估 —— **该告警的账户不告警**，最危险的错误方向 |
| 暂停投放的日子算进分母 | 那些天有指标行、`spend` 是 0，本来就该拉低日均。区分「没数据」和「没花钱」正是这个分母的意义 |
| 🔴 **只取一个层级的花费** | 同一天既有账户级又有系列级数据时全加起来就是双倍花费。取「有数据的最高层级」：`account` → `campaign` → `adgroup` → `ad` |
| 天数保留 1 位小数 | 日报里没人需要「还能撑 2.3333333 天」 |

### 什么时候告警

| 情况 | 结果 |
|---|---|
| `days_left ≤ 3` | **告警**。等号要算上 —— 阈值的语义是「留给人反应的时间」，卡在边界上时那点时间已经不够了 |
| 余额 ≤ 0 | **告警**，`days_left = 0`。广告此刻就是停的。不返回负数 |
| 近期没花钱（日均 = 0） | `days_left = null`，**不告警**。没有消耗就不会归零，报一条只会让人对告警脱敏 |
| 从没录过余额 | `getBalanceRunway` 返回 `null`（不是 404、不是 0 天）。账户是存在的，只是不知道 |
| 账户 `is_active = false` | 不出现在告警清单里。停止合作的客户余额多少都不重要 |

`null` 一律表示**无定义**，不是 0 也不是「永远够用」—— 与 glossary 里「分母为 0
返回 null」是同一条规矩。

## ⛔ 必须读源码的部分

- **日均消耗为什么只认一个层级**（`services/balance.py` 的 `_LEVEL_PRIORITY`）。
  看签名推不出来：一次查询把每个层级都汇总回来，再在 Python 里按优先级挑。全加
  起来会双倍计费 → 日均翻倍 → 可撑天数腰斩 → 一条凭空冒出来的告警，而这条告警
  长得跟真的一模一样。

- **`rules/` 够不着数据库，这条有机器强制**（`pyproject.toml` 的分层契约）。
  规则压在 `providers | db` 之下，所以想在 `rules/balance.py` 里写一句
  `select(...)` 会被 import-linter 当场拦下。要加数据来源就往 `services/` 加，
  规则只收算好的数字。

## 已知残余

- ⚠️ **两个参数都还没有业务定论**（回看 7 天、阈值 3 天）。定下来的当天只改
  `rules/balance.py` 的两个常量，并回 [glossary](glossary.md) 把值填死。
- **不做币种换算。** 余额和消耗都是账户币种，两者相除没问题；但跨账户的告警清单
  里 `available` 是几种不同的货币，**不能相加**。清单里每行都带着 `currency`
  正是为了让这件事看得见。
- **没有「余额变化」的历史视图。** 快照都在，但没有接口按时间序列返回它们（列表
  接口是分页的原始行）。真要画余额曲线时再加。
- **库存那条规则和这条是同构的，但分母难得多**（[stock.md](stock.md)）：余额的
  日均消耗从 `daily_metrics` 算得出来，库存的日均销量得靠导出带进来、或者从快照
  序列推。**两条规则共用「分母是真有数据的那部分」这条规矩**，改一条时回头看
  另一条。
