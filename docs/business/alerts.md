# 告警与巡检

**代码**：`rules/anomaly.py`（指标异动判定，**纯函数**）· `services/alert.py`（巡检
与对账）· `models/alert.py`（表与状态机）· `tasks/alerts.py`（定时任务体）·
`notifiers/webhook.py`（推送）· `schemas/alert.py` · `api/alert.py`（路由）·
`tests/test_rules_anomaly.py` `tests/test_alerts_api.py`

**范围出处**：[设计文档 §5](../design/2026-08-19-mvp-design.md) · 里程碑 D8

**OpenAPI tag**：`alerts`

## 一句话职责

**自动发现问题，并且只说一遍。**

[余额与告警](balances.md)那一篇回答「这个账户还能撑几天」，这一篇回答「谁去看、
什么时候看、看过的还要不要再提醒」。

**不负责**：解释原因和给建议（那是 LLM 那一层的事，D12–D13）、判定本身（在
`rules/`）、库存断货那条规则（还没做）。

## 接口

| operationId | 路径 | 说明 |
|---|---|---|
| `listAlerts` | `GET /api/alerts` | 巡检发现的告警，未解决的排最前 |
| `sweepAlerts` | `POST /api/alerts/sweep` | 立刻巡检一遍，不等下一个整点 |
| `listBalanceAlerts` | `GET /api/alerts/balances` | 余额可撑天数的**现算**清单 |

前两个查的是 `alerts` 表（带状态和时间线），第三个是**此刻重新算的**（包括还没到
阈值的账户）。两者不是一个东西的两种写法。

## 能读文档就够的部分

### 状态机：为什么不是每轮写一条

| 规则 | 一句话 |
|---|---|
| **同一件事同时只有一条 `open`** | 去重键是 `(account_id, kind, subject)`，由**部分唯一索引**（`WHERE status='open'`）保证，不是应用层的自觉 |
| 巡检每小时一次 | 余额可撑天数低于 1 天的账户是存在的，一天扫一次可能整个错过归零那个窗口 |
| 仍然成立 → 只刷新 | 更新 `last_seen_at` 和 `detail`，**不动 `opened_at`** —— 「这个问题从什么时候开始的」是日报要写的 |
| 不再成立 → `resolved` | 自动收掉，不用人点。留着的话清单很快全是已解决的，然后没人再看它 |
| 再次发生 → **新开一条** | 不把旧的翻回 `open`。部分索引只管 open 的行，所以同一个 subject 的历史可以有很多条 |
| 停投账户不巡检 | `is_active=false` 的不看。**已经开着的告警不会因为停投而自动 resolve** —— 那需要一次确认问题不在了，不是靠「看不见了」 |
| 巡检可以反复跑 | 对账是幂等的。所以它敢挂在定时任务上，也敢在失败后重试 |
| `subject` 是什么 | 账户里的**哪件事**：`balance`、`metric:spend`、`metric:cpa`。少了它，花费异动和 CPA 异动会互相顶掉 |
| `detail` 是**快照** | 触发时算出来的数字。日报要能写「触发时还剩 2.3 天」，而那时余额早就变了。里面的金额和比率都是**字符串** |

### 指标异动的口径

| 规则 | 一句话 |
|---|---|
| **周同比，不是日环比** | 昨天 vs 上周同一天。星期几效应是这个领域最强的周期性噪音源 —— 日环比会在每个周六和周一各制造一批假告警（设计文档举的例子原文就是「成本上升是周末 CPM 普涨」） |
| 看两个指标 | `spend` 和 `cpa`。⚠️ 只看两个是刻意的：**告警清单的价值和它的长度成反比** |
| 阈值 **±40%** | ⚠️ 待定参数，当前取 0.4，判定**含等号**。收口在 `rules/anomaly.py` 的 `CHANGE_THRESHOLD` |
| 花费涨跌都报 | 暴涨可能是出价失控，暴跌可能是被拒审或预算见底 —— 两个方向都要人当天知道 |
| **CPA 只报涨** | 成本下降是好消息，塞进清单只会稀释真正要处理的那几条。比率照样算出来，只是不告警 |
| 噪音门槛 **10** | ⚠️ 待定参数（账户币种）。**两天都低于它**才跳过 —— 「昨天花 500、上周同日花 2 块」正是最该被看见的跳变 |
| 缺任一边 → 不判 | CPA 在没有转化的那天是 `null`（无定义），拿它当基线会算出凭空的百分比 |
| 基线为 0 → 不判 | 「从 0 涨到 100」在数学上不是「涨了百分之几」 |
| 只在账户维度判 | 不逐个广告系列判。逐个判会让一次大盘波动产生几十条告警 |

### 通知

| 规则 | 一句话 |
|---|---|
| **没配就不推** | `ALERT_WEBHOOK_URL` 空着是正常状态：告警照样落库、接口照样查得到，只是不主动推 |
| **只在新开时推一次** | 每轮都推的话，一个持续三天的问题会发七十多条一样的消息，然后人把通知静音 |
| 推失败会自愈 | `notified_at` 留空，下一轮巡检当成「还没通知过」再试。不需要单独的重试队列 |
| 发通用 JSON | 不迁就任何一家的消息格式。挑一家等于把其余几家挡在门外；中间加个 n8n / 云函数转一下即可 |
| 🔴 **URL 是凭据** | 企业微信 / 钉钉 / 飞书的 webhook 地址里直接带着 key。它是 `SecretStr`，**任何日志、任何异常消息里都不许出现** |

## ⛔ 必须读源码的部分

- **先写库、再推送**（`services/alert.py` 的 `sweep`）。顺序反过来的话，推成功但
  写库失败的那条告警从此只存在于某个聊天窗口里。现在的顺序保证了：推失败时告警
  已经在库里，人打开清单还是看得到。

- **部分唯一索引是并发下唯一靠得住的东西**（`models/alert.py`）。同时跑两次巡检
  （比如 beat 投了一条、人又点了一次接口），靠「先查再写」会漏，靠数据库不会。
  ⚠️ 部分索引是 autogenerate 的盲区（[Schema 方案第四节](../design/2026-08-19-schema-migration.md)），
  改它的时候生成的 diff 不可信，必须手工确认。

- **摘要里的数字是全局的**（`SweepResponse`）。`opened` / `resolved` 数的是**告警
  条数**，跨所有账户 —— 写测试时按账户收窄，别拿它断言单个账户的行为。

- **`-Q adpilot` 和 beat 是两个独立的必需品**（`db/broker.py` 的 `beat_schedule`）。
  排期投出来的消息也要落在业务队列上；投错队列的症状和「忘了起 beat」一样，都是
  「告警一条都不来」，而那和「最近没什么问题」长得一模一样。两件事都有测试盯着。

## 已知残余

- **库存断货那条规则还没做。** 它需要一个全新的数据域（商品与库存快照，数据在店铺
  后台），分量和余额那一轮相当。公式已经在 [glossary](glossary.md) 里定了。
- ⚠️ **异动的两个参数还没有业务定论**（阈值 40%、噪音门槛 10）。定下来的当天只改
  `rules/anomaly.py` 的两个常量，并回 glossary 填值。
- **只有周同比，没有日环比。** glossary 里两个都列了，选一个的理由见上。真要加，
  那是 `rules/anomaly.py` 里多一个函数，不是改现有的。
- **只有一个通知通道，且没有分级。** 所有告警一视同仁地推同一个 webhook。真实需求
  大概是「余额告急发群、指标异动只记录」—— 等有第二个通道时再按 `kind` 分流。
- **死信队列里有东西不会告警。** 那是[异步任务](tasks.md)那边的残余，需要一条不依赖
  数据库的巡检（因为它要在数据库挂了的时候也能报）。
- **没有「静音」或「确认」。** 明知故犯的情况（比如就是打算让某个账户烧完停投）现在
  只能眼看着它每轮都留在清单上。
